## 0. 通用视觉语法（19 种共享）

### 0.1 骨架四段

几乎所有卡片都是同一套骨架的变体：

```
① 头部    图标 + 小标签 chip（可选）      或  标题 + 右侧徽标
② 标题    加粗，比正文大一档
③ 主体    正文 / 列表 / 图 / 控件 / 多行状态
④ 脚部    极细分隔线 + 标签 chips / 元信息（可选）
```

**三种头部形态**（覆盖面 100%）：

| 形态 | 例子 | 说明 |
|---|---|---|
| 图标 + 灰色小标签 | 信息卡（`▤ 知识概念`）、比较卡（`方案 A`） | 标签在标题**上方**，是「分类」不是「脚注」 |
| 纯标题 | 推荐卡、指标卡 | |
| 标题 + 右侧徽标 | 摘要卡（`摘要`）、进度卡（`完成`） | 两端对齐，徽标不换行 |

### 0.2 ⚠️ 「适合：…」不在卡片里

图鉴每种末尾都有一行「适合：概念解释、知识点摘要…」。**那是文档的说明文字，不是卡片的组成部分**
（截图里它一律在容器**外**）。实现时不要把它画进卡片。

### 0.3 文字三层（全部走 `--tk-*`）

| 角色 | 变量 | 用在哪 |
|---|---|---|
| 标题 / 正文 | `--tk-foreground` | 卡片标题、正文 |
| 副标题 / 元信息 | `--tk-dimmed` | 「Python 文档 · 教程」「匹配位置：第 12-16 段」 |
| 更弱 | `--tk-muted` | 大号数字下的单位说明、极弱注脚 |
| 禁用 | `--tk-disabled` | 不可用控件 |

### 0.4 ⚠️ 两个必须先补的地基

**① 圆角 / 阴影 / 间距在 LiMo 里没有变量族。**

`design/tokens.css` 里定义过 `--radius-md` / `--shadow-md` / `--space-4` / `--text-base`，
但那个文件**自 2026-08-14 起不再被运行时加载**（其文件头自述：「已迁移⋯此文件保留作为设计文档
参考，不再被运行时加载」），而 `index.css` 里**只有裸值**（`border-radius: 8px` 于 `index.css:437`）。

→ 卡片是**第一处会大量需要「统一圆角 + 统一阴影」**的地方。否则 19 种卡片会各自散落裸值——
正是「同一份逻辑只有一个家」要防的。

⚠️ **但不要补成通用的 `--radius-md` / `--shadow-md`**——见 **§0.7**：这一族变量同时是
「卡片视觉方案」这根新轴的**载体**，直接补成 `--card-*` 一举两得。

⚠️ **投影是这族里唯一的例外：它要分成两层**。`--sh-0`～`--sh-3` 是**全局等级**
（明暗各一套色值，挂在 `:root` / `[data-theme="dark"]`），方案层只写
`--card-shadow: var(--sh-N)`。**合成一层会让「方案 × 明暗」变成乘法**——
每套方案都得自己维护明暗两份阴影色值。理由见 §0.7 ②。

**② `--md-code-bg` 等四处的底色变量是坏的。**

`index.css:235/237/240/252/254` 与 `286/288/291/401` 引用 `var(--tk-surface-hover)`，
而这个变量**全仓只有引用、没有定义**（应写作 `--tk-hover`，或其 `@theme` 别名
`--color-surface-hover`）。按 CSS 规范，`var()` 引用未定义变量且无 fallback → 该声明
**在计算值阶段失效**。受影响：代码块底色、引用块底色、表格表头底色、斑马纹。
→ 修法：把 9 处 `--tk-surface-hover` 改为 `--tk-hover`（**一处也别漏**）。

### 0.5 语义色四态

| 语义 | 变量 | 出现处 |
|---|---|---|
| 成功 / 优势 / 完成 | `--tk-success` | 比较卡的「优势」、进度卡「完成」徽标、指标卡数字 |
| 进行中 / 信息 / 标签 | `--tk-accent` | 处理中徽标、比较卡的方案标签、图表折线 |
| 警告 | `--tk-warning` | 需注意 |
| 错误 / 限制 / 失败 | `--tk-error` | 比较卡的「限制」、进度卡「失败」、异常卡图标 |
| 中性 / 等待 | `--tk-muted` / `--tk-border` | 等待中徽标、次要描边 |

### 0.6 三个共享构件

| 构件 | 形态 | 变量 |
|---|---|---|
| **徽标 Badge** | 小圆角矩形 + 语义色文字 + 浅色底 | 前景 `--tk-{success,error,accent}`，底用同色 `color-mix(… 12%, transparent)` |
| **标签 chip** | 胶囊 + 浅底 + 弱色文字 | 文字 `--tk-dimmed`，底 `--tk-hover` |
| **主按钮** | 深色实心（截图是近黑） | 底 `--tk-foreground` / 文字 `--tk-surface`；次按钮 = 描边 + 透明底 |

### 0.7 卡片视觉方案：**默认 GPT 风，可换**（新增一根轴）

> 用户 2026-10-10 定：卡片视觉语言**照主题系统的原则做**——**默认是 GPT 那套观感，
> 但可以被换掉**。

**先分清两根轴**，它们经常被混为一谈：

| 轴 | 管什么 | 取值 |
|---|---|---|
| **骨架**（草案里的） | **要不要**卡片 | `paper`（一整张纸，现状）／ `card`（每节一张卡） |
| **卡片视觉方案**（本节） | 卡片**长什么样** | `gpt`（默认）／ …换成其他 |

**「GPT 风」到底是什么**（本文 §1–19 的截图**全部都是它**，可直接当视觉基准）：
**描边分层、几乎无阴影、大留白**；小图标 + 灰色小标签开头的头部；极细极浅的分隔线；
语义色**只用于文字**（「优势 / 限制」），**不起色块**。

**落点——照抄六轴的做法**：一个 `data-card-style` 属性 + 一组 `--card-*` 变量，
方案只换变量取值，渲染规则一行不改：

```css
/* 底色 = 基色 × 抬升，两个正交维度（见下「底色是一根派生轴」） */
:root {
  --card-bg-base: var(--tk-surface);   /* 基色：跟随哪一层背景 */
  --card-lift:    100%;                /* 抬升：0% = 完全跟随，100% = 抬升面 */
  --card-bg:      color-mix(in srgb, var(--card-bg-base), var(--tk-elevated) var(--card-lift));
}
/* 投影走等级，不写死在方案里 —— 方案只引用等级，色值随明暗自动适配 */
:root               { --sh-0: none;
                      --sh-1: 0 1px 2px rgb(0 0 0 / .04);
                      --sh-2: 0 4px 12px rgb(0 0 0 / .06);
                      --sh-3: 0 8px 30px rgb(0 0 0 / .10); }
[data-theme="dark"] { --sh-1: 0 1px 2px rgb(0 0 0 / .30);
                      --sh-2: 0 4px 12px rgb(0 0 0 / .40);
                      --sh-3: 0 8px 30px rgb(0 0 0 / .50); }

[data-card-style="gpt"] {            /* ← 默认 */
  --card-bg-base: var(--tk-surface); --card-lift: 100%;   /* 等价于 --tk-elevated */
  --card-border: 1px solid var(--tk-border-light);
  --card-radius: 16px;
  --card-shadow: var(--sh-0);        /* 靠描边分层，不靠投影 */
  --card-padding: 22px 26px;
  --card-gap: 14px;
}
[data-card-style="apple"] {          /* 示例：投影分层 + 更圆 */
  --card-border: 1px solid transparent;
  --card-radius: 14px;
  --card-shadow: var(--sh-2);
}
[data-card-style="compact"] {        /* 示例：小圆角 + 密间距 */
  --card-radius: 6px;
  --card-padding: 12px 16px;
  --card-gap: 8px;
}
[data-card-style="paper"] {          /* 示例：与页面同色，全靠描边分 */
  --card-bg-base: var(--tk-surface); --card-lift: 0%;
  --card-radius: 4px;
  --card-shadow: var(--sh-1);
}
```

**① 底色是一根派生轴，不是几个固定档。**

用户 2026-10-10 定：卡片底色要有设置「**跟随背景颜色**」或「**在背景颜色基础上稍微做点变化**」。
注意这两者**性质不同**——前者是「取某个现成色」，后者是「从它算出来」。做成两个下拉档
（「跟背景」「比背景亮一点」）会立刻暴露问题：**「亮一点」到底亮多少没有出口**，
而下一个想要的档位（「跟背景，但偏蓝」）又得再加一个。

→ 所以拆成**两个正交维度**，一个下拉 + 一个滑条：

| 维度 | 变量 | 取值 | 答的是什么 |
|---|---|---|---|
| **基色** | `--card-bg-base` | `--tk-surface`（页面底）/ `--tk-hover` / 主色淡底 / `transparent` | 卡片的底**从哪来** |
| **抬升** | `--card-lift` | `0%` ～ `100%` | 从基色**走多远** |

- `lift = 0%` → `color-mix` 结果恰等于基色本身，即**完全跟随背景**（靠描边与页面分开）。
- `lift` 中段 → 「**在背景色基础上稍微做点变化**」。
- `lift = 100%` → 纯 `--tk-elevated`，即**现状 GPT 风**。

⚠️ 三个不显然但重要的推论：

- **下拉里不再需要「抬升面」这一项**——它是「页面底 + 100%」的组合，重复列会造出
  两条通往同一结果的路径（同一份逻辑两个入口，模式 #54 的迷你版）。
- **与六轴正交**：`--card-bg-base` 引用的是 `--tk-surface` 等**语义面**，
  而语义面本身随 `data-base`（13 种基调）与 `data-theme`（明暗）变化
  → 卡片底色**自动跟随基调**，不需要第二套配色表。
- **基色选「透明」时必须禁用抬升**——`color-mix` 里的 `transparent` 是 `rgb(0 0 0 / 0)`，
  混出来是半透明**黑**，不是「在背景色基础上做点变化」（它混的是黑，不是背景）。
  这不是「少见组合」而是**无效组合**，留着就是一个拉不出正确结果、
  也看不出为什么的旋钮（模式 #53）。

**② 投影必须走「等级」，方案层一个色值都不许出现。**

方案层写 `--card-shadow: 0 4px 12px rgb(0 0 0 / 0.06)` 有两个问题：
① 违反下方硬约束（凭什么叫「纯几何量」是灰色地带，实际会变成漏网色值）；
② **暗色下会失效**——同一个 6% 黑在 `#161618` 上完全看不见，得手动加深，
于是每套方案都要维护明暗两份，而「方案 × 主题」是笛卡尔积，**维护量按乘法涨**。

→ 先定 `--sh-0`～`--sh-3` 四个**等级**（明暗各一套色值，就在上面那段），
方案只引用等级。**`--sh-*` 的定义里出现 `rgb(0 0 0 / …)` 是唯一允许的例外**——
影子本质上就是黑，且它**必须**随明暗换值（这件事只能在等级层做，在方案层做不了）。
方案层因此恒为 `var(--sh-N)`。

等级变量的定义挂在 `:root` / `[data-theme="dark"]` 上，与 `data-theme` 同源
——故「**一套骨架 × 任意方案 × 任意主题**」在暗色下依然成立，
这正是下面「硬约束」结尾那句的前提。

**维度分解——分三层，判据是「它是不是布局」**：

| 层 | 维度 | 形态 | 变量 |
|---|---|---|---|
| **① 容器七件套** | 底 / 边 / 圆角 / 投影 / 内边距 / 间距 / **内框** | **变量**（方案的主要载体） | 底 = `--card-bg-base` × `--card-lift`（**派生**，见上）／`--card-border`／`--card-radius`／`--card-shadow`（**只引用 `--sh-N`**）／`--card-padding`／`--card-gap`／`--card-frame` + `--card-frame-inset` |
| **② 内部层次** | 分隔线 / 标题色 / 弱文字 / 标签 chip / 徽标圆角 / **图标线条** | **变量**（次级，方案可选调） | `--card-divider` `--card-title` `--card-weak` `--card-chip-bg` `--card-chip-fg` `--card-badge-radius` `--card-icon-stroke` `--card-icon-cap` `--card-icon-join` |
| **③ 结构性差异** | 比较卡的**多列网格** / 时间线的**竖连线** / 代码面板的**工具条** / 媒体卡的**贴边图** | **不做变量，独立实现** | — |

⚠️ 第三层的判据：**能用一个值描述的是变量；需要改结构的是布局。**
把布局硬塞进变量，会得到「一个变量控制两件不相干的事」——那是新的耦合，比散落更糟
（也是用户说的「做特殊的可以考虑独立实现」）。

**① 层里的「内框」为什么是 `outline` 而不是再套一层 `border`**：
套一层嵌套 div 要污染 DOM 结构；`box-shadow: inset` 会和投影抢同一个属性——而
`--card-shadow` 已承载「明暗自适应的投影等级」，把内框混进去就成了「一个变量控制
两件事」。`outline` + **负的 `outline-offset`** 能在**容器内部**画第二圈线，
不占布局、不动内边距、可与 `border` 并存。国风的「印谱双框 / 线装书格线」靠的就是它。

**② 层里的「图标线条」**：同一份 path，靠 `stroke` 粗细与线帽换气质，见 **§0.8**。

**已落地的 8 套预设**（样板里可切换）：现代 5 套 —— `gpt`（默认）/ `apple` /
`compact` / `outline` / `paper`；国风 3 套 —— `guofeng`（方角双框）/ `seal`（主色粗边）/
`ink`（无框大留白）。

**国风三套的取舍**：中式视觉可用的手段**只有几何**——颜色归 `--tk-*`（硬约束），
所以国风**不能靠「加一抹朱红」实现**。落点是四条：

| 手段 | 变量 | 为什么 |
|---|---|---|
| **方角** | `--card-radius: 2px` / `0` | 中式器物方正；16px 圆角天生是「现代卡片」的语言 |
| **方头线条** | `--card-icon-cap: square` + `join: miter` | 中式线条讲究起笔收笔方正，圆头是西式线性图标的口音 |
| **框的处理** | `--card-frame` / `--card-border` | 三套的差异全在这：**双框**（印谱）/ **粗单框**（印章）/ **无框**（水墨） |
| **大留白** | `--card-padding: 30px 36px` + `--card-gap: 22px` | 纸面留白；密排是信息密集的现代取向 |

⚠️ `seal` 套用的是**主色描边**——在默认蓝色 accent 下它是「蓝章」，只有用户把
accent 换成朱红才是红章。**这是对的**：形状归方案，颜色归主题。

**硬约束（与六轴完全同源）**：`--card-*` 的值**只能引用 `--tk-*`、`--sh-N` 或纯几何量**
（px / 无单位数）。**方案里出现任何裸 hex / `hsl()` / `rgb()`，就是打破「零硬编码色值」。**
——这正是「**一套骨架 × 任意主题**」能成立的前提：**方案管几何与层次手法，颜色永远归 `--tk-*`**
（唯一的例外是 `--sh-*` 的定义层，理由见上「② 投影必须走等级」——**例外在等级层，不在方案层**）。

**三个还没定的点**（记下免得忘）：

1. **候选方案清单**——**已落地 8 套**（见上），更多待定。可继续取材的方向：
   与本仓 `data-texture`（宣纸 / 牛皮纸 …）逐一对齐的纸质变体、
   与 `components.md` 的 HIG 风更贴合的 Apple 变体。
2. **切换入口**——用户 2026-10-10 定「**可以自由组合，就像主题那样**」，即与六轴同构：
   **逐维度独立可调 + 预设包一键到位，两者并存**。`--card-*` 是唯一的变量家，
   预设包只是「一组取值」，与手动微调共用同一批变量
   （同 `THEME_PRESETS` 与各轴的关系）。具体清单（几套预设、每维度几档）待定。
3. **骨架 = `paper` 时这根轴失效**（没有卡片可画）——设置里应**隐藏或禁用**，
   否则会出现「调了没反应」的死旋钮（模式 #53：不该在「不用换」的路径上劝人换）。

**实物样板**：[pi-docs/卡片视觉方案-样板.html](../pi-docs/卡片视觉方案-样板.html) ——
**全 19 种各出一个最小实例** + 两行控件（预设包一键 8 套 / 逐项微调）。
**每个控件只改一个变量**，渲染规则零方案分支。已实机验证：同一套变量在
**8 套预设 × 明暗两侧**下全部成立，包括结构性差异最大的那几种
（竖连线 / 贴边图 / 横滚 / 节点连线 / 表格 / 代码工具条）。

⚠️ 预设与微调是**同一批变量**的两个入口，故切换预设时必须**先清空全部受控变量**
再套用新值。只写差异而不清，上一套独有的键会**残留**（国风套的 `--card-frame`
与 `--card-icon-cap` 漏到 `gpt` 上），界面上看起来像「预设切换有 bug」——
实际是「没人清」的静默串味。受控变量**从 PRESETS 派生**，不手写第二份清单。

**扩到 19 种后实测出的三条**（均已修进样板）：

1. **结构性差异一律「独立实现、不做变量」**。竖连线 / 贴边图 / 横向滚动 / 节点连线 /
   表格 / 代码工具条都是**布局**不是取值；它们只受 `--card-gap` / `--card-padding` /
   `--card-bg` 等既有变量影响，自己不新增旋钮。**判据是「换一套预设它该不该变」**——
   该变的是取值（走变量），不该变的是布局（走实现）。
2. **`guofeng` 的内框必须与外框同色**。曾写 `--tk-border-light`，实测像素 `#EBE7E2`
   对卡片底 `#F4F1EE` **只差 9 个灰阶**：线画出来了，渲染管线全对、断言全过，
   **肉眼等于没有** —— 双框这个特征整个没落地。想做「外强内弱」，CSS 里做不出粗细差
   （外框 `border` 与内框 `outline` 都只能 1px），只能同强度。
3. **媒体卡（贴边图）必须配 `overflow: hidden`**。图区是方的、卡片是圆角的，不裁就露出直角。
   这是「结构性差异」与「容器七件套」**唯一打架的地方**——解法是让图区**不参与**容器圆角，
   而不是把圆角改掉。

**三种「⛔ 交互式」卡片在样板里的定位**：⑩ 进度 / ⑪ 操作确认 / ⑫ 表单是**前端组件**，
状态归前端（附录 A 已定性）。样板把它们一并画出，只为回答「**套上同一套视觉长什么样**」——
它们的圆角 / 底色 / 边框确实跟着 `--card-*` 走（`.c-btn` / `.c-field input` 都吃
`--card-badge-radius`），这一条不证自明。

### 0.8 图标：风格变量 + 候选库（含协议）

图标在 19 种卡片里只出现在**头部**（§0.1 三种形态都有），但它是「共享构件」，故单独成节。

**① 图标风格也是变量。** 同一份 path，靠三个变量换气质：

| 变量 | 作用 | 默认（Lucide 风） | 国风 |
|---|---|---|---|
| `--card-icon-stroke` | 线宽 | `2` | `1.25` – `1.75` |
| `--card-icon-cap` | 线帽 | `round` | `square` |
| `--card-icon-join` | 拐角 | `round` | `miter` |

⚠️ **必须走 CSS 不能走 SVG 属性**：`stroke-width="var(--x)"` 在 attribute 里**不成立**，
但 CSS 的 `stroke-width` 会覆盖 presentation attribute。故骨架里的 SVG **不写死线宽**，
由 `.ico svg { stroke-width: var(--card-icon-stroke); … }` 统一注入。

**② 候选图标库与协议**（2026-10-10 逐条查证）：

| 库 | 协议 | 规模 | 气质 | 备注 |
|---|---|---|---|---|
| **Lucide** | **ISC** | ~1600 | 2px 线性、圆头 | **LiMo 已用**（`lucide-react`，51 处引用；ACKNOWLEDGMENTS 已登记） |
| **Tabler Icons** | MIT | ~5800 | 2px 线性、更几何 | 与 `outline` / `compact` 套气质最合 |
| **Phosphor** | MIT | 9000+（6 种字重） | 圆润，有 duotone | 最贴近 `apple` 套 |
| **Heroicons** | MIT | ~300 × (outline / solid) | Tailwind 官方 | 需要实心档时可选 |
| **Material Symbols** | Apache-2.0 | 3000+ | 几何，有可变字体 | 谷歌系 |
| ⚠️ **Remix Icon** | **自定义（Remix Icon License v1.0，2026-01 起）** | 3000+ | 中性几何 | 见下 |
| ⚠️ **Font Awesome Free** | **混协议**：SVG 图标 **CC BY 4.0** / 字体 SIL OFL 1.1 / 代码 MIT | 2000+ | 实心方形 | 见下 |

**两条必须知道的协议坑**（「注意协议」的价值正在这里）：

- **Remix Icon 在 2026-01 换了协议**——从 Apache-2.0 改成自定义的 *Remix Icon License v1.0*。
  实测新协议**仍允许商用 / 修改 / 随产品分发，署名可选**，唯一禁令是「不得把图标本身
  当独立图标包出售」（与 LiMo 无关）。但它是 **`NOASSERTION`（非 SPDX 标准协议）**：
  OSI 未收录、许可证扫描工具无法自动识别，**且日后可能再变**。若采用，把全文存 `licenses/`。
- **Font Awesome Free 是三份协议拼起来的**：SVG 图标走 **CC BY 4.0 → 要求署名**，
  与 MIT 类「署名可选」不同。要用就得在 ACKNOWLEDGMENTS 显式署名，且它的实心方风格
  与本文的卡片骨架（描边分层、线性图标）气质不合。

**③ 国风图标这条路：查证结论是「没有可用的开源库」。**

| 找过的 | 问题 |
|---|---|
| GoGetIcon「Chinese Traditional」144 图标 | **free with attribution，明确不是 MIT**；条款不成体系 |
| 88icon / Pngtree 等素材站 | 版权与再分发条款**含糊或禁止**；素材站常混入来源不明的转载内容，**无法追溯** |
| 主流图标库（上面那 7 家） | **一家都没有国风款**——这不是疏漏，是需求本身不成立：没有产品需要一套「水墨风通用 UI 图标」 |

更深一层：**「国风图标」是个矛盾需求**。UI 图标的第一职责是**字义清晰**，
而水墨 / 印章 / 云纹是**装饰性**的——把信息图标画成水墨，牺牲的正是可读性。

→ 故国风的风味**由几何承担**（方角 / 双框 / 方头线条 / 大留白，已在样板 `guofeng` 套
验证有效），图标**继续用 Lucide**。真要国风装饰元素（印章框 / 回纹 / 云纹），
**自绘 3–5 个 SVG**——量小、可控、零协议风险。

**④ 若哪天真做多图标集，成本是什么。**

引入第二套图标库 ≠ 多一个 npm 包，真正的工作量是**一层语义映射表**
（同一语义名 → 各库的图标名）。19 种卡片用到几十个图标位，每加一套库就要多维护一整列。

而收益是「**细看才注意到的差异**」——对照样板：圆角从 16 改成 2 的观感变化，
**远大于**换掉一整套图标。这与项目「不为未验证的需求预建机制」一致。

→ **建议第一版只落一套（Lucide）**，把「图标集」留成方案里的**预留字段**。
已经落地的「图标**变量**化」（线宽 / 线帽 / 拐角）成本为零、对国风的线条气质有实际作用
（1.25 vs 2 的粗细看得见），保留。

## 一、信息与知识类

### 01. 信息卡 Information Card

**作用**：一张卡讲清**一个对象**（概念 / 结论 / 来源）。判据是原话——「只有当这种**独立性有助于
扫描、比较或后续操作**时，才值得卡片化」；内容短就直接用正文。

```
┌────────────────────────────────┐
│ ▤  知识概念                     │  ← 图标 + 灰色小标签（--tk-dimmed）
│ 什么是向量检索？                 │  ← 加粗标题
│ 向量检索通过比较查询和内容的向量… │  ← 正文
│ ────────────────────────────── │  ← 1px --tk-border-light
│ (语义搜索) (相似度) (知识库)     │  ← 胶囊标签 chips
└────────────────────────────────┘
```

**LiMo 现状**：🆕 全新。结构上它就是「一个 md 小节的另一种画法」，**不需要新协议**。

### 02. 比较卡组 Comparison Cards

**作用**：并列对比 N 个**同级对象、统一维度**。图鉴点名的**第一优先**。

```
┌─ 方案 A ────────┐  ┌─ 方案 B ────────┐
│ (方案 A)         │  │ (方案 B)         │  ← accent 淡底小标签
│ 整体输入          │  │ 分块处理          │  ← 加粗标题
│ 一次性向模型提交…  │  │ 将长文分段处理…    │  ← 正文
│ ───────────────  │  │ ───────────────  │  ← 极细分隔线
│ 优势             │  │ 优势             │  ← --tk-success 小标题
│ 实现简单，能直接… │  │ 可以安排超长文档… │
│ 限制             │  │ 限制             │  ← --tk-error 小标题
│ 受上下文窗口限制。 │  │ 需要处理分块边界… │
└──────────────────┘  └──────────────────┘
```

**视觉要点**：列间等距；「优势 / 限制」是**彩色小标题 + 普通正文**（不是色块、不是徽标）。

**LiMo 现状**：🆕 全新，且是 19 种里**最值得做的一种**。
⚠️ 与 md 表格的分界（图鉴给的判据）：「表格更适合比较**相同字段**，尤其是**对象较多**的时候；
卡片更适合展示每个对象的**说明、重点和操作**」→ 但**具体阈值（N=2 用卡、N≥3 用表？）图鉴没给，
需自己拍**。

### 03. 推荐卡 Recommendation Card

**作用**：明确给出「**建议选 X**」及其理由。与比较卡的区别是原话——「比较卡主要支持用户
**自己判断**，推荐卡则明确提出**候选选择**」。

```
┌────────────────────────────────┐
│ ✓  建议优先采用结构化协议         │  ← --tk-success 图标 + 加粗标题
│ 推荐方案：为 LiMo 的对话实现…     │  ← 加粗前缀 + 正文（同一行内）
│ 为什么推荐：可以沿用已有图表管道…  │
│ 主要限制：需要额外处理围栏解析…    │
└────────────────────────────────┘
```

**视觉要点**：**无分隔线**；三个前缀（推荐方案 / 为什么推荐 / 主要限制）加粗但**不是标题字号**
（行内前缀，不是小节）。

**LiMo 现状**：🆕 全新。

### 04. 摘要卡 Summary Card

**作用**：快速获得长内容的**整体印象**。与信息卡的差别（原话）：「不在于外观，而在于内容
**来自一份更长的材料**，并且承担了**信息压缩**的任务」。

```
┌────────────────────────────────┐
│ 📄 AI 知识管理系统设计        摘要 │  ← 加粗标题 + 右侧灰色徽标（两端对齐）
│ 示例文档 · 3 个核心结论          │  ← --tk-dimmed 副标题
│ 1. 文档应当是知识系统的基础对象。 │  ← 有序列表
│ 2. 知识关系需要保留来源依据。     │
│ 3. 工作流是处理知识的手段，…      │
└────────────────────────────────┘
```

**LiMo 现状**：🆕 全新。⚠️ LiMo 的多篇合成产物已有「摘要」性质的节，但是**正文形态**，与此不同。

### 05. 来源与引用卡 Source Card

**作用**：让用户**找到原始材料**。图鉴核心句：「来源卡的核心**不是重复 AI 的结论**，而是让用户
找到原始材料」。

```
┌────────────────────────────────┐
│ 📄 Python 官方教程              │  ← 图标 + 加粗标题
│ 来源：Python 文档 · 教程         │  ← --tk-dimmed
│ 相关内容                        │  ← 加粗小标题
│ 函数可以将一段可复用的操作封装…   │
│ 用途：核对原始定义，追溯 AI 回答… │
│ 查看官方教程                    │  ← --md-link 下划线链接
└────────────────────────────────┘
```

**LiMo 现状**：✅ **已有等价物** —— 对话的 `tool_result.refs` 渲染成**引用文档 chips**。
形态不同（chips vs 卡片），但**职责已覆盖**。图鉴说它「特别适合知识库问答、研究资料和
跨文档综合」。

### 06. 搜索结果卡 Search Result Card

**作用**：从一组**候选**里选一个打开。

```
┌────────────────────────────────┐
│ 搜索：Python 作用域             │  ← 容器标题（多条目共用一个容器）
│ Python 变量作用域与名称查找      │  ← 条目加粗标题
│ Python 学习笔记 · 第 4 章        │  ← --tk-dimmed 来源行

│ 函数进阶笔记 · 第 2 章           │
│ …                              │
└────────────────────────────────┘
```

**LiMo 现状**：✅ **已有** —— 文档库的 `SearchSnippet` + `DocRow`。
⚠️ 图鉴自己说「结果数量很多时应采用**列表或分页**，而不是把每条做成面积很大的卡片」，
且总表里标为「**否**（不必做成卡片）」。

## 二、数据、状态与操作类

### 07. 指标卡 Metric Card

**作用**：强调**少量关键数字**。原话：「强调少量关键数字，而不是解释复杂的因果关系」。

┌──────────────┐  ┌──────────────┐

**视觉要点**：数字字号约为正文的 2–3 倍；数字本身用**语义色**（截图里 128 是绿色）。

**LiMo 现状**：🆕 全新。LiMo 目前没有「统计面板」这类场景。

### 08. 图表卡 Chart Card

**作用**：展示数据之间的**关系 / 趋势**。与指标卡的分工（原话）：「指标卡展示**重点数值**，

```
┌────────────────────────────────┐
│ 每周新增文档数量                │  ← 加粗标题
│ 用趋势辅助判断知识库的增长变化。 │  ← --tk-dimmed 副说明
│   ╭────╮                       │
│  ╱      ╲___                   │  ← 折线图（--tk-accent），浅网格线
│ ╱                             │
│ 0   第1周  第2周  第3周  第4周   │
│ 以上为虚构数据，仅用于演示…       │  ← --tk-muted 注脚
└────────────────────────────────┘
```

**LiMo 现状**：✅ **已有** —— 图表管道（` ```fig ` 语义 JSON → `chart_layout` → PIL 渲染 PNG）。
⚠️ **差别**：现状产物是「md 图片引用」，图鉴这里是「**卡片容器包住图**」——
即外层多一层卡壳。若采纳，是给现有管道**套壳**，不是重建。

### 09. 进度与状态卡 Progress / Status Card

**作用**：理解**任务当前状态**。

```
┌────────────────────────────────┐
│ ✓  文档解析                完成  │  ← 图标 + 加粗标题 + 右侧徽标
│    已完成，已提取正文             │  ← --tk-dimmed 说明
│ ────────────────────────────── │
│ ◐  生成摘要              处理中  │  ← accent 态
│    正在调用模型                  │
│ ────────────────────────────── │
│ ○  知识关联              等待中  │  ← --tk-muted 态
│ !  建立索引                失败  │  ← --tk-error 态
└────────────────────────────────┘
```

**LiMo 现状**：⛔ **明确不该由模型产出**。图鉴原话：「真正的任务状态**应该来自后端，而不是由模型
编造**」。LiMo **已有** `processingTasks` + TaskPanel（真状态、真后端）。
→ 它属于「**已有实现，且模型不得伪造**」这一桶，是「失败显式化」原则的正面命中。

### 10. 工作流 / 时间线卡 Workflow / Timeline

**作用**：理解**步骤之间的关系**。与进度卡的分工（原话）：「进度卡回答『**当前状态是什么**』，
时间线回答『**步骤之间是什么关系**』」。

```
┌────────────────────────────────┐
│ 文档进入知识库的过程             │  ← 加粗标题
│ ① 导入文档                     │  ← 编号 + 加粗步骤名
│  │  保存原始资料及来源元信息。     │  ← 缩进的 --tk-dimmed 说明
│ ② 解析与清洗                    │
│  │  提取正文并整理文档结构。       │
│ ③ 生成摘要与知识                 │
│ ④ 建立索引                      │
└────────────────────────────────┘
```

**视觉要点**：编号是**数字**（不是圆点）；竖连线从编号向下贯穿，**最后一个编号不画线**。

**LiMo 现状**：⚠️ **部分重合**——图表管道有 `timeline` / `hchain` 两种算子。
⚠️ 但那是**PIL 渲染的 PNG**，这个是**纯 CSS 列表**，更轻、可选中复制、随主题变。
→ 要不要重复建设，是**「复用还是新建」的取舍点**（口子原则的同类判断）。

### 11. 操作 / 确认卡 Action / Confirmation Card

**作用**：需要用户**明确决定**的动作。

┌────────────────────────────────┐

**LiMo 现状**：⛔ **不该由模型产出**。图鉴原话：「按钮需要**连接业务接口**，并且**后端完成权限
与状态检查后才算执行成功**」。LiMo 已有各类确认弹窗（未保存离开三态 / 删除确认 / 批量操作）。

### 12. 表单 / 配置卡 Form / Configuration Card

**作用**：直接收集参数，不必都走自然语言。

┌────────────────────────────────┐

### 13. 媒体卡 Media Card

**作用**：媒体**本身就是主要信息**（不是正文旁边配装饰图）。

```
┌────────────────────────────────┐
│ ████████████████████████████████│  ← 大图贴边，圆角跟随容器
│ ████████████  (yomu.ai)  ██████│
├────────────────────────────────┤
│ 知识整理工作台                  │  ← 加粗标题
│ 图片 · 学习资料 · 视觉参考       │  ← --tk-dimmed 元信息
│ 将图片、音视频预览或其他媒体…     │
└────────────────────────────────┘
```

**LiMo 现状**：🆕 全新。LiMo 产物里图片是 md 图片引用（`![...](assets/…)`），无卡片壳。

## 三、多媒体、追问与结构化浏览

### 14. 追问 Chips Follow-up Chips

**作用**：**降低用户继续提问时的组织语言成本**。图鉴点名的第二优先。

```
┌────────────────────────────────┐
│ 接下来可以继续了解              │  ← 加粗标题
│ 这些选项可点击，会直接向当前对话… │  ← --tk-dimmed 说明
│ (比较不同卡片)(分析视觉布局)(查看实现代码) │ ← 胶囊按钮行
└────────────────────────────────┘
```

**LiMo 现状**：🆕 全新。⚠️⚠️ **与设计草案里的「追问」不是同一件事**：

| | 追问 chips（图鉴） | 追问沉淀（设计草案） |
|---|---|---|
| 点击后 | 发一条**普通用户消息** | 答案 **append 进产物 md** |
| 答案落在哪 | **对话历史** | **文章里** |

图鉴原话：「它们**只负责将文本作为普通用户消息发送，不承担其他业务操作**」。
→ 两者是**两级**：chips 是入口（省打字），沉淀是另一个动作。分工待拍板（草案 §5.4）。

### 15. 数据表格 Table View

**作用**：对比**结构化字段**。

```
┌────────────────────────────────┐
│ 文档处理结果                    │
│ 文档        状态        耗时     │  ← 表头（浅底 --md-table-header-bg）
│ Python 笔记  (完成)     2 秒     │  ← 状态列是彩色徽标
│ 研究论文     (处理中)    —       │
│ 扫描 PDF     (失败)      5 秒     │
└────────────────────────────────┘
```

**LiMo 现状**：✅ **已有** —— `.markdown-body table` + `.md-table-wrap` 横向滚动 + 斑马纹。
⚠️ 图鉴总表标为「**否**（不必做成卡片）」；且给了判据：「表格更适合比较**相同字段**，
尤其是**对象较多**的时候；卡片更适合展示每个对象的说明、重点和操作」。
⚠️ 受 §0.4② 影响：表头底色与斑马纹当前**是坏的**。

### 16. 轮播卡组 Carousel

**作用**：**容器**——按顺序浏览多个同类对象。

```
┌────────┐ ┌────────┐ ┌────────┐
│ ▤      │ │ ▤      │ │ ▤      │  ← 小图标
│ 网页资料 │ │ 视频资料 │ │ PDF 论文│  ← 加粗标题
│ 提取正文…│ │ 获取字幕…│ │ 解析正文…│  ← 说明
│ 文本来源 │ │ 视频来源 │ │ 文档来源 │  ← --tk-hover 浅底标签
└────────┘ └────────┘ └────────┘
```

**LiMo 现状**：⚠️ 图鉴标为「**否**，是一种容器」。且它自己提醒：「如果用户需要**同时比较**
很多项目，**横向滚动可能不如表格或展板直接**⋯不应该把所有卡片都做成轮播」。

### 17. 代码 / 技术内容面板 Code Panel

**作用**：阅读代码。

```
┌────────────────────────────────┐
│ 一个最小 Python 示例            │  ← 加粗标题
│ 函数：封装可重复调用的逻辑        │  ← --tk-dimmed 副标题
│ ┌────────────────────────────┐ │
│ │ </> Python        ⧉   ▶ 运行 │ │  ← 工具条：语言标签 + 复制 / 运行
│ │ def summarize(text: str)…   │ │  ← 语法高亮（--md-code-bg 底）
│ │     return text[:100]       │ │
│ └────────────────────────────┘ │
└────────────────────────────────┘
```

**LiMo 现状**：✅ **已有** —— rehype + 语法高亮 + 代码块。⚠️ 图鉴原话：
「代码区域通常需要保持**等宽字体、缩进和复制能力**。**不要为了统一视觉而把代码改成普通
文字卡片**，否则会影响可读性和可用性」——保住语义，别为了好看牺牲可用。

### 18. 提醒 / 异常卡 Alert Card

**作用**：突出**异常 / 风险 / 重要条件**。

```
┌────────────────────────────────┐
│ ⚠  文档处理失败                 │  ← --tk-error 图标 + 加粗标题
│ 原因：无法从扫描 PDF 中获得有效…  │
│ 当前结果不完整，不能作为正常…     │
│ 建议处理方式                    │  ← 加粗小标题
│ 检查文档是否为扫描件，再明确启用… │
└────────────────────────────────┘
```

**LiMo 现状**：⚠️ 形态全新，但**原则逐字同源**。图鉴原话两条：
「它**不应该只用颜色制造紧张感**，而应当明确告诉用户**出了什么问题、有什么影响，以及下一步
如何处理**」「失败卡**不能掩盖真实错误**，也不能**只显示一个红色的『失败』标签，而不说明原因**」
→ 与 LiMo 的「**失败显式化 / No silent degradation**」一字不差。做成卡片时这是硬约束。

## 附录 B · 图鉴给 LiMo 的 4 条硬提醒（原文）

这几条与项目既有原则**逐字同源**，做卡片时必须守：

## 附录 C · 两种判据的分野（本文最易被混淆处）

图鉴与 `pi-docs/产物呈现形态与追问-设计草案.md` **站在不同的一侧**：

| | 图鉴（本文件） | 设计草案 |
|---|---|---|
| **落点** | 对话回答 | 产物文章 |
| **卡片化判据** | **内容形态**（并列对比才用） | **结构**（按 H2 切节，全都用） |
| **追问答案落在哪** | 对话历史（chips = 省打字） | **append 进产物 md** |

**后果**（决定成本量级）：

- **产物侧**有天然的 H2 结构 → **纯前端**，零协议、零 prompt、存量文档立刻受益
- **对话侧**没有可靠结构 → 只能让模型吐语义（围栏）→ 要新增协议，
  并处理简报 §9.4 已识别的难点：**流式打字机撞上半截围栏**
  → **2026-10-11 已落地**（`limo-block` 对话侧，解法是**整行抑制**：尾行的半截标记行不渲染，
  见 `markdown-scan.ts::suppressTrailingPartialMarker`）

**两者治的不是同一个病**：产物骨架治「**信息密度**」（全局观感），
内容型卡片治「**局部表达**」（并列对比这类）。**互补，不互斥。**
