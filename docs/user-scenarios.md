# 用户场景

> 这些场景是系统设计的出发点。架构的存在是为了服务这些场景，不是反过来。

---

# 一、场景

## 场景 1：一篇好文章，不想收藏夹吃灰 ✅ 已实现

你在刷 RSS / Twitter / 公众号，看到一篇讲 RAG 架构的长文。你觉得有用。

**系统处理：**
- 清洗排版（去掉广告、推荐阅读、评论区）
- 产出干净的 Document.content

**产出 Document：** 一篇干净、可读、可搜索的文章正文。

**此时你已经可以：** 保存 / 搜索 / 自己读。

**进一步处理（可选）：**
- 生成 200 字中文总结
- 提取关键词：RAG、Retrieval、Embedding、向量数据库

**你做什么：** 看一眼总结——还行，点保存。

**一个月后：** 搜 "RAG retrieval generation"，找到这篇，看到当时的总结，快速定位到关键段落。

**你要的不是"收藏"，是"消化后的备忘"。**

---

## 场景 2：一个视频教程，想变成可检索的文字 ✅ 已实现

B站看到一个 40 分钟的教程，讲本地部署 DeepSeek。讲得很好，但你不想再看第二遍。

**系统处理：**
- 爬取视频（平台可能需要登录，验证 cookie）
- 分离音频和画面
- 音频 → 转写 API，得到完整文字稿
- 关键画面帧 → 视觉模型描述（"展示了 ollama 的命令行参数界面"）
- 合并成一篇带截图说明的技术文档

**产出 Document：** 一份可搜索、可复制的文字版教程。

**此时你已经可以：** 直接搜 "ollama 参数" 定位到相关段落。不需要进一步处理。

**进一步处理（可选）：**
- 生成教程大纲摘要
- 提取命令行操作步骤

**你要的不是"下载视频"，是"把视频变成文字文档"。转录本身就完成了这个任务。**

---

## 场景 3：一篇 PDF 论文，里面有图表 ✅ 已实现

一篇讲电池回收的论文，PDF 格式。文字可以 OCR，但里面有流程图和实验数据表格。

**系统处理：**
- OCR 提取文字
- 识别图表区域 → 视觉模型理解图表含义
- 表格 → 结构化提取

**产出 Document：** 文字正文 + 图表的文字描述 + 结构化表格数据。可读、可搜索。

**此时你已经可以：** 搜关键词找到相关段落，看图表描述理解实验设计。不一定需要总结——你可能想看全文。

**进一步处理（可选）：**
- 生成论文摘要（核心发现和方法）
- 提取关键数据点

**用户两种典型用法：**
- "我先看总结，决定值不值得精读" → 要总结
- "我已经知道这篇很重要，我就要看全文" → 只要转录

**你要的不是"PDF 转文字"，是"理解图表内容"。转录已解决。**

---

## 场景 4：自己写的零散想法，想整理 ✅ 已实现

你在备忘录里写了几段关于某个项目的想法，零零散散。

**系统处理：**
- 去废话，保留有信息量的句子
- 按主题分段
- 识别"这是描述问题 / 这是解决方案 / 这是待办"

**产出 Document：** 结构化的思路文档——分过段、分过类、去掉了重复表述。可读。

**此时你已经可以：** 得到一个比原版清晰很多的版本。

**进一步处理（可选）：**
- 归纳核心主题
- 提取可行动的要点
- 标注"这里有遗漏"或"这部分需要展开"

**你要的不是"笔记软件"，是"思路整理"。转录 = 整理结构。进一步 = 识别问题和行动点。**

---

## 场景 5：想验证某个说法是不是真的 ✅ 已实现

文章里写 "GPT-4 的训练成本是 1 亿美元"。你觉得不靠谱。

**前提：** 文章已处理为可读文字。

**进一步处理：**
- 从 Document 中提取可验证的声明
- 调搜索 API，找到可靠来源
- 交叉验证：
  - 这个数字来自某篇报道，原文说的是"可能超过 1 亿"
  - 没有公开确认的精确数字
- 标注可信度：中等偏下

**你做什么：** 决定保留这篇文章，但标注"这个数字存疑"。

**这个场景没有标准化——它发生在转录之后。它是对已有 Document 的二次加工。你要的不是"搜索"，是"交叉验证"。**

---

## 场景 6：同一件事，不同来源说法不一样 ❌ 未开始

你有三篇文章，关于同一个技术方案。一篇说效果好，一篇说有严重缺陷，一篇说在特定场景下适用。

**系统处理：** 三篇各自清洗，产出三份干净的 Document。

**此时你已经可以：** 各自搜索、各自阅读。

**进一步处理（可选）：**
- 并排呈现三篇的核心观点
- 标注观点冲突点（"A 声称 X 效果好，B 声称 X 有缺陷"）

**关键约束：系统不替用户总结"谁对谁错"，不给出"综合结论"。只呈现差异，用户自己判断。**

**你要的不是"正确答案"，是"看到全貌"。**

---

## 场景 7：聊天记录 → 提取讨论要点和待办 ❌ 未开始

微信/钉钉/Slack 里一个群聊了几百条。你不想爬楼。

**与场景 4（零散想法）的区别：** 场景 4 是一个人写的，场景 7 是多人对话——有说话人、有回复关系、有对话结构、语言碎片化。

**系统处理：**
- 按说话人分段（依赖聊天平台导出格式）
- 识别对话线程（谁在回复谁）
- 区分"讨论过程"和"最终结论"
- 去社交噪音（"好的""收到""哈哈"）

**产出 Document：** 结构化的讨论记录——按话题分组、标注说话人和时间、区分讨论和结论。

**此时你已经可以：** 直接看"结论是什么"，不用爬楼。

**进一步处理（可选）：**
- 提取待办项 + 对应负责人
- 标注"这个话题有结论" vs "这个话题没聊完"

**你要的不是"聊天记录存档"，是"从噪音里捞出结论和待办"。**

---

## 场景 8：多语言内容 ✅ 已实现

一篇英文论文，或者一篇日文技术博客。你看不懂原文，或者看原文太慢。

**系统处理：** 翻译全文 → 母语版本。

**产出 Document：** 一份母语的内容。可读、可搜索。

**此时你已经可以：** 读完整内容，搜关键词。

**进一步处理（可选）：** 生成母语总结 + 关键词提取。

**用户的三种选择（系统不替用户决定）：**

```
原文
  ├─ 选 A：我只要翻译全文（想自己读）
  ├─ 选 B：我只要总结（不想花时间）
  └─ 选 C：我都要（先看总结，有用再看全文）
```

**你要的不是"翻译工具"，是"用我能懂的语言消化内容"。选项交给用户。**

## 场景 9：对已存内容 AI 对话

你已经存了若干篇。不想一篇篇翻，想直接问。

### 9a：对单篇提问 ✅ 已实现

你存了一篇 RAG 总结。里面写了"检索和生成通过中间表示衔接"，你看不懂。

**你做什么：** 选中这篇，问系统："什么叫中间表示？具体是什么数据结构？"

**系统做什么：**
- 读取这篇 Document
- 定位相关段落
- 用 AI 解释给你听

**这和搜索的区别：** 搜索告诉你"哪篇文档提到过中间表示"。对话告诉你"中间表示就是向量格式，检索返回的文档被转成 embedding 后拼到 prompt 里"。

### 9b：跨多篇讨论 ❌ 未开始

你存了三篇关于 RAG 的总结，分别讨论了不同方案。

**你做什么：** 选中三篇，问："这三种方案里，检索延迟最低的是哪个？"

**系统做什么：**
- 读取三篇 Document
- 理解你的问题
- 比较三篇里关于延迟的信息
- 综合回答

**v1 范围：** 用户手动勾选一篇或几篇，对选中内容提问。系统基于选中内容回答。**"自动找到所有相关文档来参与讨论"不在 v1。**

**你要的不是"全文搜索"，是"对话理解"。**

## 场景 10：截图 / 手写笔记 → 数字化 ✅ 已实现

你拍了一张白板上的架构图，或者会议时手写的几页笔记。

**系统处理：**
- 手写 OCR 识别
- 白板图 → 视觉模型理解（"一个系统架构图，左侧是输入层，右侧是输出层"）

**产出 Document：** 数字化的文字 + 图像的文字描述。可搜索。

**此时你已经可以：** 搜白板上的关键词，找到这张图。

**进一步处理（可选）：** 如果手写内容零散，可以整理结构（同场景 4）。

**你要的不是"云相册"，是"让非数字的东西能被搜到"。**

# 二、核心设计洞察

## 2.1 获取的两条路径

10 个场景里，用户导入的方式天然分两种：

**直接导入：文件/文本已在本地，不需要获取层。**

| 场景 | 用户操作 | 直接得到 |
|------|---------|----------|
| 3 PDF | 拖文件 | 本地 PDF |
| 4 零散想法 | 粘贴文本 | 文本 |
| 7 聊天记录 | 粘贴/导出 txt | 文本 |
| 10 手写/截图 | 拖图片 | 本地图片 |
| 1 文章（已复制） | 粘贴正文 | 文本 |

用户给了什么，就是什么。跳过获取层，直接进转录管道。

**间接导入：用户给链接，系统去拿。**

| 场景 | 用户操作 | 需要经过 |
|------|---------|----------|
| 2 视频 | 粘贴 B站/YouTube 链接 | 识别平台 → 认证 → 下载 → 落地 |
| 1 文章（链接） | 粘贴网页 URL | 下载 HTML |
| 8 外文 | 粘贴链接 | 下载原文 |

系统需要先完成获取，落地为本地文件，再进转录管道。

**同一个入口，两条路径：**

```
用户操作
    │
    ├─ 拖文件 / 粘贴文本 → 直接导入 → 转录管道
    │
    └─ 粘贴链接 → 间接导入 → 获取层 → 落地 → 转录管道
```

**关键：不是所有东西都需要获取层。先判断输入类型，再选路径。**

## 2.2 转录 → 消费（架构转向后的新模型）

### 原始转录是核心，消费是平级操作

```
任何来源
    │
    ▼
┌──────────────────────┐
│  转录层（适配器）      │  ← 必须跑，每种来源一条管道
│                       │
│  视频→ASR+VL+字幕     │
│  PDF→OCR+图表理解     │
│  聊天→结构化+去噪音    │
│  外语→翻译            │
│  手写→识别            │
│  网页→正文提取         │
│  零散想法→类型识别     │
└──────────────────────┘
    │
    ▼
  RawTranscript（核心存储，一等公民）
    │
    │  此时用户已经可以：存了，搜得到
    │
    ├─────────────┬─────────────┐
    ▼             ▼             ▼
  [生成面板]    [次级工具]    [AI 对话]
  MD+目录+总结   事实验证       半屏/全屏
  +关键词        提取待办       讨论问答
                 多方对比
```

**关键变化：** 不再有"必须跑的转录管道"。转录之后，用户直接存储 RawTranscript。Markdown 视图、"帮我消化"、事实验证——都是从 RawTranscript 出发的平级操作，没有先后依赖。

## 2.3 关键结论

**1. 转录是管道，消费是工具箱。平级，不串行。**

转录解决一个问题：**"任何东西都能变成机器可读的文字。"**

消费解决另一个问题：**"要不要生成 Markdown / 总结 / 验证 / 对比？"**

**2. 不是所有场景都需要进一步消费。**

| 场景 | 转录后用户已经满足？ | 消费的价值 |
|------|----------------------|-----------------|
| 2 视频 | ✅ 得到可搜索文字稿，够了 | 想要大纲/步骤摘要时再用 |
| 3 PDF | ✅ 能读图表描述了，够了 | 想快速判断值不值得精读时用总结 |
| 4 零散想法 | ✅ 已分段归类，比原版清晰 | 想要行动清单时再用 |
| 6 多方观点 | ✅ 各自已有干净文档 | 想并排对比时再用 |
| 8 多语言 | ✅ 已有母语版本 | 不想读全文时用总结 |

**3. 用户决定是否消费，不是系统默认生成。**

系统不应该默认"导入 → 总结"。用户导入视频、PDF、聊天记录时，转录完成就可以停了。Markdown 视图和总结都是用户主动触发的操作。

## 2.4 原始转录 vs Markdown 视图

**原始转录是一等公民，Markdown 是按需视图。**

以视频为例：

```
RawTranscript（Whisper JSON + VL 描述 + 字幕，完整、精确）
      │
      ▼
Markdown 视图（人读、特定风格、可换参数重新生成）
```

**Markdown 视图是有损的：**

一段 Markdown 里丢掉了什么：
- 每一帧画面出现了什么——只挑了"关键帧"
- ASR 置信度——哪句话可能听错了
- 原始分段——转录引擎按沉默期切分还是按语义切分
- 全量时间戳——只保留了几个起止标记

**如果以后用户想：** 换个风格、更精简、更详细、或者"画面描述太少了多补一些"——从 Markdown 已经回不去了。只能从 RawTranscript 重新生成。不需要重新支付转录成本——转录已缓存。

**两者的关系：**

```
RawTranscript（核心存储）
      │
      ├─→ Markdown 视图 v1（详细版）
      │
      ├─→ 换风格 → Markdown 视图 v2（精简版）
      │       从 RawTranscript 重新调 LLM，不重跑转录
      │
      ├─→ 换粒度 → "把画面描述里的 UI 操作提取成步骤清单"
      │       从 RawTranscript 提取全量画面描述
      │
      └─→ 跨系统迁移 → 输出成另一个系统要的格式
              RawTranscript 是完整信息源
```

**两者定位：**

| | RawTranscript | Markdown 视图 |
|------|------|------|
| 定位 | **母版**——完整、精确的机器可读记录 | **衍生品**——人读的、特定风格和粒度的展示 |
| 稳定 | 不随展示风格变化 | 有不同版本和粒度 |
| 给谁用 | 系统自己、后续处理、跨系统迁移 | 人读、搜索、分享、引用 |
| 内容 | 所有信息（全量时间轴、全量置信度） | 筛选后（人关心的关键段落） |
| 废弃 | 不展示给用户，但保留 | 可以重新生成 |

**RawTranscript 是"底片"，Markdown 视图是"冲印出来的照片"。照片可以换风格重新冲印，前提是底片还在。**

## 2.5 设计原则

从实践中提炼的核心判断：

1. **从场景反推架构。** 先写场景，再从场景推导需要什么，不先画架构再往场景上套。
2. **砍到找不到下一个可合并的。** 不是"只能有 N 个概念"，是找不到第 N+1 个不可消解的。
3. **复杂度后置。** v1 跑起来后通过插件长出来的东西，不是 v1 不重要的东西。
4. **中间态保留。** 原始转录是母版，衍生品是视图。每一步可回退、可重生成。
5. **变化因素隔离。** 获取层变化来自平台，转录层变化来自模型——两者独立。
6. **用户决策点前置。** 用户决定要不要进一步处理、信不信、存不存。

# 四、场景共同点

| 维度 | 共同点 |
|------|--------|
| 输入 | 来源多样，形态各异。非文字的变文字，看不懂的变能懂 |
| 转录 | 必须跑，产出 RawTranscript——存下来就能搜 |
| 消费 | 用户可选，平级操作。Markdown 视图、总结、验证——从 RawTranscript 出发 |
| 用户决策 | 用户决定：存不存、信不信、要不要生成视图或进一步加工 |
| 核心诉求 | **把任何东西变成能存储、能搜索的文字。要不要再加工，用户说了算。** |

# 五、明确不在 v1 范围

| 不做的事 | 为什么 |
|----------|--------|
| 自动给出"正确答案" | 系统不做仲裁，只呈现多方观点 |
| 自动删除"低质量"内容 | 用户判断价值，系统不替用户决定 |
