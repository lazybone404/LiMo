## 一、现状：字面检索（已落地）

```
写入侧                                    查询侧
──────                                    ──────
update_index(engine, store, tx_id)        search(query, limit)
  ↓ 判据：doc_text.search_index_text        ↓ _tokenize(query, limit=64)
rawText + 最新版笔记                        ↓  CJK 二字组 + 英文词 + 数字串
  ↓ _clean_for_search（不分词、不截断）      ↓ _escape_fts5 → OR 连接
  ↓ _tokenize（不封顶）                     ↓ FTS5 MATCH ... ORDER BY rank (BM25)
{title, body(UNINDEXED), toks} 三列         ↓ _make_snippet（从 body 取原文）
```

### 三条不能动的判据

| 判据 | 为什么 |
|---|---|
| `_tokenize` 的 `limit` 默认 **None** | 索引侧必须收全文。曾经无条件 `uniq[:64]`，每篇只索引开头 64 个 token，而所有单测都是短文本、全绿 |
| 查询用 **OR** 不是 AND | 二字组 AND = 一票否决，语义型查询归零（15 题 7→0） |
| `body` 列 **UNINDEXED** | 摘要是给人看的。token 化是检索的内部表示，不能泄漏到展示层 |

### 五个写点

摄入 / 重新转录 / 生成完成 / 编辑保存 / 启动重建 —— 全部经 `update_index()`，
内容判据只有 `search_index_text` 一处。

### 1.1 索引坏了会怎样：三态，且必须能看见（2026-10-26）

**「搜不到」是一个会撒谎的界面。** 索引库损坏、文件被占用、启动重建失败 ——
这三种情况下后端此前都会走到「搜索返回空数组」，而用户看到的是**与「库里没有这个词」
逐字相同**的一句话。没有任何入口能告诉他「检索这一路压根没跑」。

现在分三态，判据落在 `SearchEngine` 自己身上：

| 状态 | 判据 | 用户看到 | 谁能修 |
|---|---|---|---|
| 可用 | `available is True` | 正常结果 | — |
| **索引不可用** | `available is False` + `lastError` | 列表里一条提示：索引不可用 + **去处**（设置 → 通用 → 检索索引） | 用户：点「重建索引」 |
| 引擎不在场 | `QueryService._search is None` | `QUERY_NO_SEARCH_ENGINE`（500） | 开发者：构造时机错了 |

四条不能动的判据：

1. **构造失败不抛**（`__init__` 捕获后记 `_lastError`）。改造前 `SearchEngine(...)`
   在 `main.py` 的 try **之外** —— 一个坏掉的 `search.db` 会让整个 FastAPI startup 崩，
   用户的知识库**打不开**，而所有文档其实好好躺在磁盘上。检索是一个能力，不是一个前置条件。
2. **两个错误码必须分开**：`QUERY_INDEX_UNAVAILABLE`（503 + `recoverable=True`）vs
   `QUERY_NO_SEARCH_ENGINE`（500 + 不可恢复）。前者用户点一下就能修，后者他根本无从下手 ——
   合并成一条等于把人送去查一个并不属于他的初始化顺序。
3. **写入端不抛**：`index()` / `delete()` 在不可用时**直接返回**。让它们抛会把
   「检索坏了」升级成「文档导入失败」，那是拿一个可修复的问题去污染数据写入。
4. **`status()` 是纯只读**（2026-10-26 审查 P1-02）：读状态（`SELECT count(*)`）失败只记进
   返回值新增的 `statusError` 键，**绝不写 `_last_error`**。`available` 的定义就是
   `_last_error is None` —— 一次瞬时读失败（磁盘忙 / 库被占）写进去，等于「用户在设置页
   看一眼」换来一个**只有手动重建才解除**的不可用状态，而界面上不会说发生了什么。
   `VectorStore.status()` 同款做法。⚠️ `statusError` 前端类型有、界面**刻意不展示**
   （用户对它没有可采取的行动，重试即可）。

**自愈只在 `rebuild()` 里**（`_recover_db()`：删掉 `search.db` / `-wal` / `-shm` 三个文件重来）。
`index()` 没有「从头灌一遍」的能力，所以**设置页那个按钮是唯一出路**，不是锦上添花。

⚠️ **Windows 上踩到的坑**：`delete` 报 `WinError 32 另一个程序正在使用此文件`。
根因是 `_conn()` 返回裸 `sqlite3.Connection`，而 `with conn:` 只做 commit/rollback、
**不关闭文件句柄** —— 于是「删掉损坏的库重建」这条路**从来就走不通**，失败表现只是
「重建后依然不可用」，没有任何线索指向文件占用。修法是把 `_conn` 改成
`@contextmanager`（`finally: conn.close()`）。这条是被
`test_rebuild_recovers_from_corrupt_db` 实测抓到的，不是读代码想到的。

### 1.2 空间回收：只有「用户主动重建」才 VACUUM

`search.db` 的 `auto_vacuum=0`，删除的页留在文件里。实测本机库：**137 行 / 14.74MB，
其中 879 / 3774 页是空闲 —— 23% 是垃圾**（`body` 列是近全文副本，删一篇就留一大块）。

- **启动重建不 VACUUM**：每次「打开应用」多等一次全库重写，收益却为零（用户看不见）
- **`POST /api/search/reindex` 才 VACUUM**：这是用户主动点的，代价在确认框里已经说过
- 判据用 `PRAGMA freelist_count`（精确、平台无关），**不用文件大小**（页大小 / WAL 残留
  会让阈值只能写成「大概」，而大概的断言在实现退化时也可能绿）

## 二、向量检索：为什么做

### 2.1 先回答「我们的数据属于哪一类」

业界判断「该不该上向量」的常用判据不是复杂度，是**数据结构化程度**：

| 维度 | 非结构化（法律文档 / 知识库） | 结构化（代码库） |
|---|---|---|
| 检索方式 | 语义匹配，找同义词近似词 | 字面精确，错一个字就匹配不上 |
| 变化频率 | 几年才变 | 经常变 |
| 索引维护 | 变更少，成本低 | 每变一次都要重建 |
| 适合方案 | 传统 RAG / embedding | grep / BM25 / Agentic Search |

Claude Code 落在右边那一列，所以它用 grep 而不是 RAG —— **这是数据形态决定的，不是路线之争**。

LiMo 的文档库落在**左边**那一列：视频转写、网页、论文、个人笔记，全是自然语言；
而且导入后基本不再变（比「几年才变的法律文档」更稳定）。**索引维护成本在我们的场景里趋近于零**，
这恰恰是 Claude Code 拒绝传统 RAG 的那条理由在我们身上不成立。

⚠️ **但两者的检索入口形态也不同，这一点不能忽略**：Claude Code 的检索发生在 **agent loop 里**
（可多轮改写查询），而 LiMo 的搜索框是**单轮、250ms 消抖、要求即时**——没有 agentic 多轮试探的余地。
Boris 那句权衡 `Agentic search can outperform RAG, but at the cost of latency and tokens` 里的
「at the cost of latency」正是我们这个入口付不起的东西。
（对话侧那条是 agent loop，它走的是 `search_docs` 工具，与搜索框是两条路径。）

### 2.2 29 题实测

29 题实测，两路失手题**几乎完全错开**：

| | 失手（131 篇库） |
|---|---|
| 字面（83%） | 4 道纯语义改写 + `1048` |
| 向量（86%） | 3 道专有名词 + `1048` |
| **交集** | **仅 `1048`**（数字规范化问题，与检索方式无关） |

RRF 融合上限 **97%**（k=10，等权）。

**本地模型也是同一结论**（`bge-small-zh-v1.5` ONNX int8，22.8MB，CPU，零 torch）：
137 篇库上纯向量 83%、RRF **93%**，字面基线 79%。**相对排序与云端那轮完全一致。**

| | 纯向量 | RRF(k=10) | 成本 | 外发 |
|---|---|---|---|---|
| 云端 `text-embedding-v4` | 86% | **97%** | ~2 元/次全量 | 全库正文出网 |
| 本地 bge-small int8 | 83% | **93%** | 0 | 零 |

> ⚠️ **跨轮数字不能直接比**：云端那轮 131 篇 / 基线 83%，本地这轮 137 篇 / 基线 79%。
> 「97% vs 93%」里混着分母变化，**不能读成「云端模型更好」**。

> ✅ **两组数都能独立复现，且不依赖 `_experiments/`**（2026-10-26 补 `--vector`）：
> `python scripts/eval_search.py --vector` 直接打出字面 / 纯向量 / RRF 三路，137 篇库上
> 复现 **79% / 83% / 93%**，**逐题失手清单与原实验逐条一致**。
> 实验脚本 `_experiments/02-embedding-rrf/eval_ab.py` 仍保留（它做「多切块策略扫描」，
> 产品脚本不做那件事），但两边的 `Embedder` / 切块 / `rrf` 已收编成同一份
> `backend/scripts/embed_local.py` —— 各自抄一份正是
> [01-lexical-search](../../_experiments/01-lexical-search/README.md) 里那 40pp 落差的成因。

> ⚠️ **29 题样本小**，1 题 = 3.4pp，97% 的置信区间很宽，k=10 也未必是最优
> （实测 k=60 是 90%，与业界默认相反 —— 因为一路第 1、另一路很差时会被拉平）。
> 落地时保留 `k` 可配。

> 🔬 **已在公开数据集上复核（2026-10-26，`mteb/EcomRetrieval`，10 万条 × 1000 题）**：
> 详见 [_experiments/03-public-datasets/](../../_experiments/03-public-datasets/README.md)。
> 三条结论，两打折一条成立：
>
> | 结论 | 在 1000 题上 |
> |---|---|
> | 向量 > 字面 | ✅ 成立，且差距更大（64.2% vs 49.1%，+15.1pp） |
> | 融合有收益 | ⚠️ **量级缩小一个数量级**：+1.7pp（1:2）/ +0.1pp（等权），而这里 +10pp |
> | **RRF 等权优于加权** | ❌ **被推翻**：等权次优，最优是 `字面:向量 = 1:2`；且等权的 nDCG/MRR **低于纯向量** |
> | k=10 优于 k=60 | ✅ 原样成立 |
>
> **为什么融合的收益差 10 倍**：RRF 等权隐含「两路排名同等可信」。这里两路精度 79% / 83%（差 4pp）
> 且失手几乎不重叠（交集仅 1 道）⇒ 假设成立；Ecom 上是 49% / 64%（差 **15pp**）⇒
> 给低精度信号一半话语权的直接后果就是排序指标下降。
> **所以落地时权重不能写死等权**，而且 `k` 与权重是**耦合**的（给字面加权后 k=60 反超 k=10）。
>
> ⚠️ **Ecom 测不到切块与长文档聚合**（一条商品标题就是一块），它复核的是「检索方案」这一个变量。
> 这不推翻上面那两张表（那些是在 LiMo 自己的库上测的），它给出的是**适用边界**。

> ⚠️ **这是「一次性检索 vs 一次性检索」的对比**，不能拿去跟 agentic 方案比 ——
> 有公开实验显示 agentic + 纯 BM25 可以打败一次性 embedding 切块检索（代价是延迟与 token）。
> 这不推翻本计划（我们的入口没有 loop 的余地，见 2.1），但引用这个数字时必须带上限定。

> ⚠️ **切块上限是模型能力的硬约束，不是可调参数**。`bge-small` 的 `max_length` 是
> 512 token ≈ 400–500 中文字，照搬云端的 2000 字符会让后半段被 tokenizer **静默截断** ——
> 实测 1000 字符块只有 76%，比不做向量（79%）还低。见 §3.2。

## 三、架构：引擎 + 存储 + 融合层

### 3.1 EmbeddingEngine（新增引擎类别）

与 OCR / ASR / Doc 同款，注册进 `EngineRegistry`：

```python
class EmbeddingEngine(Protocol):
    name: str                      # 展示名
    model_id: str                  # 落库用于失效判定（换模型 = 全量重建）
    dimension: int
    async def embed(self, texts: list[str]) -> list[list[float]]
```

**内置 `dashscope-embedding`**（`text-embedding-v4`）：
- 走已有的 dashscope provider key + OpenAI 兼容端点，**核心零新依赖**
- 判据来自「口子原则」四标准：依赖不重、无协议问题、跨平台无碍、无法律风险 → **留核心**
- 这是它与 whisper（CUDA）/ tesseract（280M）/ docling（torch 2GB）的区别 ——
  那三个是因为重才出核心，云端 embedding 不重

**阶段 1 已落地（2026-10-26）**——两个文件 + 三处接线，**零行为变更**（没人绑定它，等于不存在）：

| 落点 | 内容 |
|---|---|
| `engines/embedding_base.py` | `EmbeddingEngine` Protocol + `l2_normalize`。⚠️ **刻意不继承 `core.protocols.Engine`**：那个 ABC 的 `execute()` 对本类是「必须实现却永不被调用的空壳」，而空壳最坏的不是多写三行，是下一个人会以为它有用 |
| `engines/embedding_dashscope.py` | `DashScopeEmbeddingEngine`。硬数字来自官方文档：单次 `input` **≤10 条**（超了 HTTP 400）、单条 ≤8192 token（超了**静默截断**）、`dimensions` 可选 2048/1536/**1024（默认）**/768/… |
| `core/registry.py` | `ENGINE_CATEGORIES` / `ENGINE_CATEGORY_ORDER` 加 `embedding`（末位）、`ENGINE_CAPABILITY_LABELS` 加 `"embedding": "向量"` |
| `engines/__init__.py` | 在 OCR 段之后**无条件注册**（与 OCR 同款）；⚠️ 刻意不写 `engine_models` / `engine_bindings` —— 那是阶段 2 |
| `tests/test_embedding_engine.py` | 三条契约 + 批 ≤10 + **按 `index` 重排** + 条数/维度不符显式报错 + 注册可见（11 条） |

引擎侧三条契约（`embedding_base` 模块文档，测试逐条钉住）：

1. **返回顺序与入参一一对应** —— OpenAI 兼容端点的 `data` 数组带 `index` 但**不保证有序**，
   按返回顺序 append 会让「文本与向量错位」：检索质量下降、**零报错**、单测全绿（假数据通常恰好有序）。
2. **向量已 L2 归一化** —— 余弦退化成点积。归一化放协议模块而不是各引擎里：两份实现
   （`math.hypot` vs numpy）会在极小模长上分叉，失效形态是「两个引擎的余弦不可比」，只有混用时才看得出来。
3. **空输入返回空且不发起调用** —— 否则「空列表」也会白白要求一份 Key。

⚠️ **Key 缺失的抛点刻意在 `client` property，不在 `__init__`**：`init_engines` 无条件注册它，
设置页要在「没配 Key」时也能列出并显示「未配置」。搬到 `__init__` 会被那里 `except Exception`
吞掉 → 引擎整个消失，用户看不到「有这个东西、只是没配」。

**本地模型走插件口子**（`EnginePlugin v1` 的 embedding 分支）：bge-m3 / ollama 等 1–2GB 依赖、
有 CPU/GPU 差异 → 插件化。索引时机 / 触发方式 / 使用时机（何时建、何时用、增量还是全量）
**已设计，见 §6.1**。

⚠️ **2026-10-27 状态已变**：插件加载路径**已实现** —— `plugin_loader.EmbeddingPlugin` 基类 +
`_PluginEmbeddingAdapter`（进程外常驻子进程），参考实现
[local_embedding_plugin.py](../backend/plugins/examples/local_embedding_plugin.py)。
内置的 `local-bge-small` 与插件版**并存**（同名覆盖，§6.1（6）），契约见
[plugins.md](plugins.md#向量化插件embeddingplugin-v1)。

### 3.2 向量存储

**异库：`{data_dir}/vec.db`**（字面索引仍是 `search.db`）。⚠️ 这一条 **2026-10-26 修订过** ——
原设计写的是「同库不同表」，改的理由是三条**现在就存在**的机制，不是预优化：

| 理由 | 一旦触发会发生什么 |
|---|---|
| `SearchEngine._recover_db()` **删整个文件**（`.db` / `-wal` / `-shm` 一起 unlink） | 字面索引坏一次，把「几秒重建」偷偷升级成「**整库重花一次编码钱**」 |
| SQLite 写锁是**库级**的 | `rebuild()` 的大事务会与向量 worker 的批量写盘互相阻塞 |
| `rebuild(vacuum=True)` 会搬全表 | 为回收 FTS 的碎片，顺带搬几百 MB 的向量 BLOB |

代价只有两个 WAL 文件；跨库事务根本不需要 —— `vec_state.tx_id` 本来就是**软引用**
（删除文档时由 `ingest.py::_drop_vectors` 同步清两表；崩溃 / 半途失败留下的孤儿靠
§4.6 的对账兜底）。

⚠️ **DDL 的唯一真相源是 [`core/vector_store.py`](backend/app/core/vector_store.py) 的 `_CREATE_SQL`**，
下面只记形状与理由（改表请改那份，别改这里 —— 设计稿与实现各存一份 DDL，两边都会「看起来对」）：

```sql
CREATE TABLE vec_meta (            -- 单行（id=1 CHECK），记录本库向量的"身份"
    model_id TEXT,                 -- 换模型 → 整库失效
    dimension INTEGER,
    chunk_size INTEGER,
    schema_version INTEGER,        -- 索引口径版本（切块规则 / 向量编码方式）
    built_at TEXT
);
CREATE TABLE vec_chunks (
    tx_id TEXT, chunk_idx INTEGER,
    text TEXT,                     -- 原文分块（块级比对 + 调试；**不展示给用户**）
    text_hash TEXT,                -- 块级指纹 —— 增量判定的唯一依据（见 §4.4）
    vec BLOB,                      -- float32 打包
    PRIMARY KEY (tx_id, chunk_idx)
);
CREATE TABLE vec_state (           -- 文档级状态：进度 / 失败 / 脏标记
    tx_id TEXT PRIMARY KEY,
    content_hash TEXT,             -- 建索引时 search_index_text 的哈希；**pending 时置空**
    chunk_count INTEGER DEFAULT 0,
    status TEXT NOT NULL,          -- 'ok' | 'pending' | 'failed'（校验在写入处，不加表级 CHECK）
    fail_count INTEGER DEFAULT 0,  -- 连续失败次数（≥3 停 worker）—— 花钱的闸门
    error TEXT,                    -- 最后一次失败原因（给状态区展示）
    indexed_at TEXT
);
CREATE INDEX idx_vec_state_status ON vec_state(status);   -- worker 取 pending 走它
```

⚠️ **`schema_version` 现在没有就不该上线**：以后改切块规则或向量编码方式时，老索引会继续按旧规则
算、两边都报「成功」—— 与 `_EMPTY_CONTAINERS` 那类「静默失配」是同一个形态。它的初值是 `1`。

- ✅ **`vec.db` 放在 `{data_dir}/vec.db`（2026-10-26 阶段 2 第 2 步拍板）**。
  这条曾挂在这里等决策（「10 万块 × 1024 维 ≈ 400 MB，`~/.limo` 会被同步」），
  最后的结论是**不拆**，理由只有一条但很硬：

  **向量必须与它描述的那批文档同生共死。** 固定放 `%LOCALAPPDATA%` 会让「用户配了
  两个 `data_dir` 并在其间切换」变成**静默错位** —— A 库的向量被 B 库拿去检索，
  余弦照样算得出一个数、结果照常返回、界面上完全看不出来。这比「四元组不符」更难查：
  后者至少还有判据，跨库错位连判据都没有（要修得再往 `vec_meta` 塞一份 `data_dir`，
  而它带来的「换个库就整库失效重算」本身就是一笔莫名其妙的账单）。

  反过来，「`~/.limo` 会被同步」是**不便**不是**正确性**：最坏是同步工具多传几百 MB，
  且**只对主动开启了向量检索的用户**发生。体积的真实上限见 §3.2.2（1 万篇 ≈ 5.2 GB），
  到那个量级用户的备份策略本来就要重做。⇒ **`vec.db` 是纯派生缓存，删掉只会导致重算**，
  这句写在这里供用户自行排除同步。
  ⚠️ 它和 `secrets.bin` 不构成反例：那个去 `%LOCALAPPDATA%` 是为了**安全**（明文密钥不该
  进同步目录），不是体积；`vec.db` 里没有任何秘密，全是能从正文重算出来的东西。
- **文档得分 = 各块余弦最大值**（不是平均 —— 平均会稀释「只有一段相关」的长文档）
- ⚠️ **切块策略已 A/B，结论与原设计相反**（2026-10-26，137 篇，RRF k=10）：

  | 策略 | 纯向量 | +RRF k=10 | 块数 | 编码 |
  |---|---|---|---|---|
  | 字面 FTS5（基线，完全不做向量） | — | 23/29 (79%) | — | — |
  | **固定切 200 字** | **83%** | **86%** | 35,031 | 179.5s |
  | 固定切 400 字 | 76% | 83% | 17,525 | 230.8s |
  | H2 切 200 + 完整标题 | 79% | 86% | 35,286 | 212.5s |
  | H2 切 400 + 完整标题 | 76% | 83% | 17,892 | 219.8s |
  | H2 切 1000 + 完整标题 | 76% | 86% | 7,589 | 179.1s |

  **默认用固定字数切（按 `\n\n` 段落累积，不切断段落），不按 H2 切。**
  原设计是「H2 语义边界 + 块前置标题」，实测没跑赢。

  ⚠️ **看「纯向量」列，不要看 RRF 列** —— 融合会把向量路的退化掩盖掉。最清楚的是
  H2 1000 那一行：RRF 与固定切 200 **打平**（都是 86%），但它的纯向量只有 76%，
  **比完全不做向量的字面基线（79%）还低**。原因是 1000 字的块在 `max_length=512`
  下有一半内容从未进向量（静默截断），全靠在融合里由字面路把缺失补回来。
  ⇒ **RRF 数字衡量的是「两路合起来的下限」，不是向量质量本身。**
  代价是：如果哪天用户关掉字面路（或字面路退化成不含笔记），这 10 个百分点的窟窿会当场露出来。

  ⚠️ **编码成本 ∝ token 总量，不 ∝ 块数**：H2 1000 只有 7,589 块却要 179.1s，
  固定切 200 有 35,031 块要 179.5s —— 几乎一模一样，因为两者覆盖的字符总量相近、
  而超长块被 `max_length` 截掉的部分**不计入实际编码量**（但也不进向量，见上条）。
  ⇒ **切块策略省的是存储与检索内存，不是钱**；反过来，「大块更便宜」这个直觉在这里是假的。

  ⚠️ **历史读数 93% 是「只看开头」的 93%，别拿它跟今天比。** 同一套脚本、同一批 137 篇，
  04:26 那轮固定切 200 是 6,561 块 / 29.4s / RRF 93%，今天重跑变成 35,031 块 / 179.5s / RRF 86%。
  **不是库变大了**（实测这个库 rawText 均值 4.27 万字、索引文本 4.76 万字，只为原文的 1.12 倍），
  而是当时 `chunk_flat` 对**超长段落直接截断**（`c[:size]`）：这个库很多正文不带空行分段，
  `text.split("\n\n")` 只得到一整段 ⇒ 每篇只索引了开头约 **22%**。
  那是 `1095d67`（08:21，与本文档正文重做同一笔提交）修掉的缺陷，
  同期记录里 T2Retrieval 那 118,605 篇「Hit@5 91.1%」也是同一形态。
  ⇒ **截断反而让指标更高**（93% vs 86%）：文档开头通常正是主题句，噪声又少。
  这正是「指标好看 ≠ 实现正确」最典型的形态，也是本库必须留下**同轮对照**的原因。

  **一条旁证**：两轮的字面基线**逐条一致**（23/29，六条失手完全相同）。
  FTS5 不分块、索引全文，天然不受 `chunk_flat` 影响 —— 若真是「语料变了」，
  字面读数不可能一模一样。**这比对账比任何解释都硬。**

  ⚠️ **H2 标题缺陷已修，但实测净效果为零**（同库同题对照，逐档完全一致）：

  | 档 | 修正前（`^##\s+\S`，只取首字） | 修正后（`^##\s+\S.*` + 剥首行） |
  |---|---|---|
  | H2 200 | 纯向量 79% · RRF 86% · 35,595 块 | 纯向量 79% · RRF 86% · 35,286 块 |
  | H2 400 | 纯向量 76% · RRF 83% · 17,969 块 | 纯向量 76% · RRF 83% · 17,892 块 |

  **为什么修了却没变化**：`body` 是从标题位置切的、**本身包含标题行**，所以那个 `"## 标"`
  是「多塞了一个无意义短前缀」（噪音），而不是「丢掉了信息」。修完净信息量只多出
  「完整标题代替首字」这一点点，落在 29 题的噪声里看不出来。
  ⇒ **这是方法论上的一课：缺陷的严重性必须实测，不能靠读代码想象。**
  一个读起来「明显有 bug」的正则，实际损失可以是零；反过来，
  如果修完就宣布「H2 提升了 X%」，那 X 必然来自别处的波动（语料、缓存、并发负载）。

  ⚠️ 同时排除了一个解释：**「H2 没跑赢固定切」与标题缺陷无关**（修正前后都比固定切低）。
  至于真正原因（「H2 切出的块长度极不均匀，而余弦在长度相近的文本间比较才稳定」）
  **仍未做消融验证** —— 需要「H2 切但不加标题」一组，所以仍是推测不是结论。

  原始输出：`_experiments/02-embedding-rrf/results/ab-chunk-2026-10-26-h2fix.txt`（修正后五档）
  与 `ab-oldh2-2026-10-26.txt`（修正前两档，同一库同轮）。
  契约钉在 `tests/test_vector_index.py`（完整标题 + 不重复 + 只有标题的节不丢）。

  ⚠️ **这张表是在 `bge-small-zh-v1.5`（512 维 / 512 token / 本地 ONNX）上做的，不是云端
  `text-embedding-v4`**（2026-10-26 补注）。v4 是 1024 维、8192 token、**按量计费**，
  块长与块数的成本曲线都不一样 —— 「200 字最优」**不能直接搬过去当结论**，
  云端档要单独跑一轮。否则就是「换个模型、拿旧结论当新事实」，正好落进下方
  「切块上限由模型 `max_length` 倒推」那条要防的坑里。
- ⚠️ **切块上限由模型 `max_length` 倒推，不能照抄**：`bge-small` 是 **512 token ≈ 400–500 中文字**。
  原设计写的「H2 内超过 1000 字符再切」会让后半段被 tokenizer **静默截断** ——
  不报错、块看起来完整，只是那半段永远搜不到（实测 76%，比不做向量还低）。
  那个阈值是给 `bge-m3`（8192 token）写的。**换模型必须重算这个数。**
- ⚠️ **表格单独处理**：表格被切碎后每一行都失去表头，向量会读成毫无意义的短句。
  至少保证「表头 + 若干行」留在同一块内（产物里的 `table` 块有 `limo-block` 围栏可用来定位）
- ⚠️ **规模闸门**：137 篇固定切 200 = **35,031 块 / 179.5s 建库 / 71.7 MB 向量**（实测），
  纯 Python + numpy 全量余弦仍是毫秒级 —— 这个库已经在「单机可承受」的上界附近，
  而它只是 137 篇。规模账见 §3.2.1。

| 落点 | 内容 |

三条写死的语义（`test_vector_store.py` 17 条钉住）：

1. **`mark_pending` 把 `content_hash` 置空** —— 留旧值会让 worker 的快速路径
   「hash 相等就跳过整篇」在内容已变时**错误命中**，且零报错。
2. **`mark_pending` **不删** `vec_chunks`** —— 块级 hash 增量要靠旧块比对（§4.4），
   删了就只能整篇重编码。
3. **`mark_pending` 归零 `fail_count`** —— 内容变了就是一次新机会；而 `fail_count` 的
   闸门语义仍然成立（worker 反复失败且不经过写点时照样能累到上限）。

⚠️ **这一步是干净的停点**：表建好了、写点在打标记，但**没有任何查询路径读它、也没有
worker 消费它** ⇒ 对用户零影响（连 `vec.db` 都不会有非空的 `vec_chunks`）。
下一步（worker）才让索引自己长出来，再下一步（查询融合 + 开关）才对用户可见。

→ worker 已落地（**§4.7**），查询融合与开关也已落地（**§4.8**）：开了 `search.vector_enabled`
之后索引会自己长出来、且**立刻被查询路径读到**。两条缺一不可 —— 只有 worker 时它只有成本、
没有收益；只有融合层时它在用一份永不更新的索引。

### 3.2.1 建索引的门槛：在 20 篇左右，但这个门槛基本没意义

先把成本算清楚（用实测的编码速度，不用估的）。

⚠️ **块数与篇数之间没有固定系数**，此前这里按「10 块/篇」估，**低估了 25 倍**：
本库实测 **256 块/篇**（137 篇 / 35,031 块，平均 4.27 万字/篇 —— 这个库全是长视频转录，
一篇就是一次访谈）。一篇 3,000 字的短笔记只有约 16 块。下表按 256 块/篇（**上界**）算：

| 库规模 | 块数（256 块/篇） | 向量体积（512 维 fp32） | 建索引耗时 | 暴力检索耗时 |
|---|---|---|---|---|
| 100 篇 | 25,600 | ~52 MB | ~2 分钟 | <2 ms |
| 500 篇 | 128,000 | ~260 MB | ~11 分钟 | 5–10 ms |
| 1,000 篇 | 256,000 | ~520 MB | ~22 分钟 | 10–20 ms |
| 10,000 篇 | 2,560,000 | ~5.2 GB | ~3.6 小时 | 0.5–1 秒 |

（编码速度按本库实测 **195 块/秒**：35,031 块 / 179.5s，`bge-small` int8 本地 ONNX；
T2 长文本批实测过 90 块/秒，见 `_experiments/03-public-datasets/`，取哪个取决于块长与 batch 组成。
换 `text-embedding-v4` 是 **1024 维**，体积 ×2，且走云端按量计费、吞吐另算 —— 见 §3.1）

⚠️ **体积这一列是本轮新增的，它比耗时更要紧**：1000 篇就要 520 MB，
而 1 万篇 5.2 GB —— 比整个 `~/.limo` 的数据目录还大几倍。
这也是上一条「`vec.db` 不该躺进会被同步/备份的目录」的**量化依据**，不是洁癖。

**所以「到什么量级才建」这个问法，前提就站不太住** —— 只要做成后台 + 增量，
建库本身从来不是用户感知得到的事。真正存在的门槛是：

| 库规模 | 建议 | 理由 |
|---|---|---|
| **< 20 篇** | 不建 | 字面检索一搜就有，向量纯属多余 |
| **20 篇以上** | 建议开 | 一次性成本且可后台做 —— **按字符量估，不按篇数**：20 篇短笔记约 5 秒，20 篇长访谈约 30 秒 |

⚠️ **「20 篇」是形状不是阈值**：它的意思是「多到字面开始漏」，不是「过了这条线成本就跨过某个坎」。
一个 200 篇、每篇 500 字的库，比 20 篇长访谈还便宜。上面第一张表按 256 块/篇是**上界**，
拿它做预算就是拿最贵的库给最便宜的库报价。

**判据不该是篇数，而是「字面够不够用」** —— 100 篇短标签式笔记字面能到 100%，
100 篇长文 + 抽象查询可能只有 50%。但 LiMo 现在答不了这个问题：没有查询日志，算不出字面命中率。

故**不做自动判断，给一个诚实的默认**：开启时界面写「当前 1,234 篇，预计 2 分钟，可随时中断」，
让用户按体感决定。硬猜「你的库属于术语同源还是异源」，猜错了比不猜更糟 —— 用户会以为系统懂他。

⚠️ **唯一要拦的场景是批量导入**：一次进 500 篇以上时得先问一句，
别让用户在不知情的情况下等十几分钟、占掉 260 MB（按上文上界估）。

### 3.2.2 规模上限：暴力检索的拐点在 50 万块

（384 维 float32 口径）

| 块数 | 内存 | 暴力检索 | 结论 |
|---|---|---|---|
| 10 万 | 150 MB | 20–40 ms | 暴力最优 |
| 50 万 | 750 MB | 100–200 ms | 仍是暴力 |
| 100 万 | 1.5 GB | 200–500 ms | 开始难受 |
| > 100 万 | — | — | 才需要 HNSW / `sqlite-vec` |

**拐点在 50 万块 ≈ 5 万篇笔记**（按 10 块/篇）。个人知识库到不了这个量级 ——
所以**除非做成团队版，永远不需要 ANN**。不提前引入依赖这条纪律在这里继续成立。

⚠️ **向量侧不存在「因规模重建」**，只有三种重建理由（见 §4.4）。这条与字面侧不对称：
FTS5 有碎片化问题（累计写入 > 文档数 × 2 时跑 `optimize`），而向量表只有增删改，没有碎片概念。

### 3.3 融合层

```
query ──┬─→ 字面 search()             → [id...] （top 50）
        └─→ embed(query) → 余弦        → [id...] （top 50）
                                        ↓
                              RRF: score = Σ 1/(k + rank)   k=10
                                        ↓
                                   最终 top N
```

只用排名不用分数 —— BM25 与余弦量纲不可比，归一化会引入新超参。

**为什么先 RRF、不先 rerank**：两者解决的是同一个问题（把对的排前面）。RRF 零模型零成本、纯本地排序；
rerank 是第二个模型调用（每次查询都花钱 + 增加延迟）。先用 RRF 拿基线，实测仍不够再上 rerank——
但**它是明确的后备选项，不是没想到**。

⚠️ **两者能救的不是同一批题**：RRF 只重排「两路都召回了的东西」，一路召不回的正确文档它救不了；
rerank 是在**已有候选集内部**精排，收益上限取决于候选集里有没有正确答案。
所以真上 rerank 时，「召回多少条去精排」与 `k` 必须一起调 —— 只调一个，数字会好看得莫名其妙或难看得知其所以然。

**已落地（2026-10-26）**：算子 `core/vector_index.py::rrf` / `vector_rank_scored`（与评测同一份，
产品侧不另写）；编排 `services/vector_search.py::VectorSearcher.fuse()`。落到实现上的三个数：

- `DEFAULT_DEPTH = 50`，实际取 `depth = max(limit, DEFAULT_DEPTH)` —— **两路必须同深度**，
  否则「字面第 20 名」与「向量第 20 名」拿到不同的 `1/(k+rank)`，排序取决于谁取了更深的那个巧合。
- `RRF_K = 10`（29 题实测优于 60）。
- `QUERY_TIMEOUT = 3.0` 秒 —— 单条短文本一次往返，正常 <500ms；再长就是「用户以为搜索卡住了」。

#### 两个消费方，同一份编排（2026-10-29）

上面说的是**怎么融**；「一次融合检索按什么顺序做哪几步」抽在
[`services/search_fuse.py`](../backend/app/services/search_fuse.py)::`fused_search`：

```
GET /api/search  ─┐
                  ├─→ fused_search(svc, searcher, q, limit) ─→ {hits, semantic}
对话侧 search_docs┘      ├─ 字面先跑（svc.search_resources，depth 条）
                         ├─ searcher is None → semantic: null，纯字面结束
                         ├─ searcher.fuse(...) → RRF 定序
                         └─ 语义独有命中 → get_resource 回补 title
```

**抽出来的理由是修一个静默失效，不是整理代码**：对话侧的 `search_docs` 此前走
`store.list_transcripts({"query": q})` —— 那是**标题子串过滤**，既不碰 FTS5 也不碰向量。
正文里逐字存在的词只要标题没有就搜不到，而界面上表现为「AI 说库里没有，可我用搜索框
自己搜得到」，两边都不报错。两处各写一遍编排的失效形态正是这个：**一边在融合、一边没在
检索**，而两者都「能搜到东西」（模式 #54）。

四个成对要点：

1. **结果带 `snippet` 不带 `sourceType`** —— 后者在对话侧零消费方（grep 过 prompt 与前端），
   留着只会让下游多一处 `?? ''`。
2. **`found` 与 `hasMore` 分开** —— `found` 是「返回了几条」（对话侧上限 5），不是「命中了几篇」。
   不拆开时「命中 200 篇」会被摘要说成「找到 5 个相关文档」，那不是省略，是说假话。
   探测法同产品侧 `search_resources` 的 `size+1`：请求 `limit=6`，拿到 6 条即知还有更多。
3. **索引坏时降级为标题过滤并标 `degraded`** —— `fused_search` 刻意**不吞** `QueryError`：
   `/api/search` 要把它变 503（可恢复标记），对话侧要降级（抛出去会被 `agent.py` 吞成
   `{"error": …}` ⇒ 索引坏一次，对话从此搜不到任何文档）。两种处置都对，差别只能由调用方
   决定。但降级**必须说出来**——静默降级会让模型把「没搜到」当事实。
4. **向量开着时每次工具调用花一次 query embedding** —— 改造前这条路径纯内存、零成本。
   默认关 ⇒ 默认零成本；开了就是已知代价（一次短文本编码）。

## 四、索引时机（云端内置这一支必须先定）

字面索引是**同步、无成本、必成功**的；embedding 是**异步、有 API 成本、可能失败**的。
两者不能塞进同一个同步路径。

### 4.1 写入：字面先落，向量后补

```
update_index()                        ← 五个写点共用，行为不变（同步，快）
  ├─ 字面索引（现有）
  └─ vec_state: status='pending'      ← 只打标记，**不删 vec_chunks**（见 §4.4）

后台 worker（异步，独立循环）
  ├─ 取 pending → 分块 → 逐块比 text_hash → 只编码变了的块 → 写 vec_chunks
  ├─ 失败：status='failed' + fail_count+1 + 记原因，**字面检索不受影响**
  └─ 引擎不可用 / 未开启：整批跳过，状态显式可见
```

⚠️ **写点只打标记、不同步编码**。一次编码几百毫秒会卡住「保存」按钮，用户会以为卡死了。

**为什么不阻塞写入**：生成/编辑的响应时间不该被一次 embedding 网络往返拖慢；
而字面检索已经 79–83%，向量只是增量收益 —— 慢一步可用，强过卡住主流程。

⚠️ 但这违反「失败显式化」吗？不违反，**前提是状态可见**：设置页显示
「向量索引：128/131 篇 · 3 篇失败（重试）」，而不是静默只索引了 128 篇。

### 4.2 触发点

**先分清两层**（2026-10-27 起）：「什么时候**该**干活」是**调度层**（`_should_run` 的攒批闸门），
「干多久、干哪些」是**执行层**（`run_once`）。改造前这两层是一层 —— 写点只打标记不叫醒任何人，
由 60 秒轮询统一推进，于是新导入一篇最多等满一分钟才建索引而用户无从得知。

| 时机 | 动作 | 粒度 |
|---|---|---|
| 用户开启向量检索 | 全库标记 `pending` + 后台批量补（进度可见） | 全库 |
| 五个写点任一触发 | 该篇标记 `pending` + **叫醒 worker**（只是叫醒，跑不跑看闸门） | 单篇 |
| 用户点「立即建立索引」 | 跳闸门跑一轮**增量**（`_force` 旗标 + 唤醒，不另起协程） | 全部积压 |
| 用户点「重试失败项」 | **先 `requeue_failed()` 把 `failed` 全部打回 `pending`**（清 `fail_count` 与 `content_hash`），再同上一行跑一轮 | 全部失败项 |
| 用户关闭向量检索 | 后台 worker 停；**数据保留不删**（重新开启不必重算） | — |
| 启动时 | 补跑上次未完成的 `pending` / `failed`（与字面索引的启动重建同一次机会） | 全部积压 |
| `vec_meta.model_id` 不匹配 | **标 `needs_rebuild`、向量侧整体停用**，等用户确认后才重建（旧向量维度可能不同，绝不能混用） | 全量 |
| `vec_meta.chunk_size` 不匹配 | 同上（切块方式变了，旧块的 hash 对不上新切法） | 全量 |
| `vec_meta.schema_version` 不匹配 | 同上（视改动：格式转换或全量重建） | 全量 |

**前三种（开启 / 写点 / 立即建立索引）是增量，后三种（`vec_meta` 三处不匹配）是重建**。
「重试失败项」也是增量（外加一次状态重置），「关闭 / 启动」是生命周期动作。
判据：前三种改的是「某一篇的内容」，后三种改的是「所有向量的含义」—— 换模型/换切法之后，
旧向量与新的**不可比**，留着只会让余弦算出没有意义的数。

#### 4.2.1 攒批闸门：`auto` / `manual` 两档（2026-10-27）

`search.vector_trigger` 两档、`search.vector_threshold`（默认 100）一个数：

- **`auto`（默认）**：`pending` + 尚可重试的 `failed` 攒够阈值才跑一轮。
- **`manual`**：永不自动跑，只有「立即建立索引」才动。

**为什么默认是攒批**：本地引擎的模型加载 3–5 秒、常驻约 90MB，为一两篇反复
「加载 → 编码 → 释放」是纯浪费；`immediate` / `idle` 两档下它会随每一轮抖动。
攒到一批再处理，**加载次数与批次数成正比，而不是与文档篇数成正比**。

⚠️ **代价要如实记**：对小于阈值的库（含绝大多数个人库），`auto` 档等于**不会自动建索引**。
这是用户 2026-10-27 明确拍板的取舍（原话「模型只在重建的时候加载」），补偿是三条可见性：
状态区「待索引 N 篇」/ 恒在的「立即建立索引」按钮 / `trigger` + `threshold` 回显。

⚠️ **闸门住在执行层之外**：`_should_run()` 排在 `_next_ids` 与 `_warm` **之前** ——
「达不到阈值就不加载模型」因此是**结构保证**而不是调用点的自觉。顺序反过来的失效形态是
「每轮先载入 22.8MB 再判断没事干」，行为上看不出区别，只有内存曲线知道
（`test_vector_worker.py` 用 `eng.warm_calls == 0` 钉住）。

⚠️ **重试不受闸门约束**：`failed` 且 `fail_count < MAX_FAIL` 是**纠错**不是**增长**，
被挡会让一篇坏文档永远等不到重试。上限由 `fail_count` 自己承担（`MAX_FAIL = 3`）。

⚠️ **「立即建立索引」救不回已达上限的失败篇，出口是另一个按钮**（2026-10-27 记，同日补上按钮）：
`force` 跳过的是**闸门**，不是 `_next_ids` 的取件范围 —— 后者只取 `pending` 与
`retry_ids(max_fail)`，故 `fail_count >= MAX_FAIL` 的篇在**两档、「立即建立索引」下都不会**
再被尝试一次。这是刻意的（重试是计费调用，让坏文档无限抖动比停下来更糟）。

出口是设置页状态区那个 **「重试失败项 N」** 按钮（`POST /api/search/vector/retry-failed`，
**只在 `docs.failed > 0` 时渲染**）：它调 `VectorStore.requeue_failed()` —— 一条 UPDATE 把
**全部** `failed` 篇打回 `pending` 并 `fail_count = 0`、`error = NULL`，然后 `request_sync()`
跑一轮（与「立即建立索引」同一条路，不另起协程）。区别于「立即建立索引」：后者不动状态，
所以谁能被取到取决于**历史**；前者**用户的一次点击重置 `fail_count`**，把决定权交给用户。

⚠️ **`requeue_failed` 必须清空 `content_hash`**：失败项里有「先成功后失败」的篇（改了内容、
第二次编码失败），hash 还是上次成功的值 → worker 的整篇快速路径判「hash 相等」直接
`mark_ok`，**一次编码都不发却显示成功**。清空后走分块比对，`vec_chunks` 仍在 ⇒ 块级增量
照旧生效，重试不是整篇重花钱（这也是为什么**不删 `vec_chunks`**）。

⚠️ **不许把 `force` 放宽成「忽略上限」**：那会把一次误点变成一次对全部坏文档的计费扫描，
且没有任何一步是用户明确要求的。判据同「失败显式化」——**决定权在用户手上**，不在默认行为里。

⚠️ **阈值不是「多久检查一次」**：它与 `DEFAULT_INTERVAL`（心跳）是两件事，混为一谈会得出
「改成 600 秒也能达到目的」—— 那只让单个文档更晚被索引，抖动一点没少。

⚠️ **它也不是 §4.5 砍掉的「积压阈值（pending ≥ 50% 才显示进度条）」**：那条是**显示**的阈值
（结论是「永远显示更好」），这条是**执行**的闸门。`manual` + 「待索引 3 篇」是正常状态，
不是「功能坏了」。

⚠️ **后三种「不自动重建」是 2026-10-26 加的**（原设计写的是「整库失效重建」）。字面索引重建免费，
所以它可以自动；而向量重建**要花钱**，自动执行等于「用户换了个模型，程序自作主张替他花了一笔」。
判据与产物侧「换模型需要用户确认」同一条。

⚠️ **停用必须是显式的**（状态区 + 检索结果旁一行「语义检索需重建」）：悄悄退回纯字面会让用户
以为「向量没帮上忙」，实际是「压根没跑」—— 与 §4.3 那条同款。

⚠️ **四元组（`model_id` / `dimension` / `chunk_size` / `schema_version`）任一不符，向量侧就是
「整体不可用」，不存在「降级用」这一档**。硬算的失效形态最坏：余弦照样算得出**一个数**，
检索照常返回文档，只是排序毫无意义 —— 而界面上完全看不出来。故开库时校验，不符即停用。

### 4.3 查询：embedding 失败怎么办

- 查询 embed 失败 → **退化为纯字面**，结果照给，但 UI 要显示一行「语义检索暂不可用」
- ⚠️ 不能静默退化：用户会以为「向量没帮上忙」，实际是「向量压根没跑」

**已落地（2026-10-26）**：`fuse()` 返回 `{error, hits}`，`error` 非空 = 本次只用了字面结果。
三处细化：

1. **前置校验先于编码**（`_precheck`）：库不可用 / 没建过 / 口径不符三档，各自一句用户能据此
   行动的话（等后台建完 / 去重建 / 无自助手段）。命中时**一次编码都不发** —— 对着一份明知
   不可用的索引去花一次 API 调用，是纯浪费。
2. **`hits` 恒在且必须留**：它区分「开了但索引还空」（`hits: 0, error: null`）与「压根没开」
   （整个 `semantic` 是 `null`）。少了它，两者在界面上逐字相同 —— 同 `webSearch.hits: 0` 的取舍。
3. **`load_matrix` 走 `asyncio.to_thread`**：同步读盘几十到几百毫秒，放在事件循环里会让同一
   请求周期内的其它协程（worker 的 await、SSE 心跳）一起停住。

### 4.4 增量的粒度：块级 hash，不是文档级

这是整套设计里最关键的一个决定。最朴素的实现是「文档变了就重编码整篇」，
但那会浪费掉 90% 的计算 —— 用户改一个错别字，整篇 15 个块全重算。

```
编辑保存 → 重新分块 → 逐块比 text_hash
  · hash 没变的块 → 直接复用旧向量
  · hash 变了的块 → 只编码这几块
  · 块变少       → 删多余行
  · 块变多       → 只编码新增的
```

改一句话，通常只重编码 1 个块，成本从「整篇 200ms」降到「10ms」。

⚠️ **比对按「内容」匹配，不按「块下标」匹配**（2026-10-26 实现时改强的一条）。
旧向量存成 `hash → vec` 的映射，而不是 `下标 → vec`：位置匹配在「在**开头**插入一段」时
会把后面每一块的 `旧[i]` 与 `新[i]` 错开一位 ⇒ **整篇重编码**。两种实现都不报错，
差别只在账单上；`test_vector_worker.py::test_insert_paragraph_does_not_reencode_everything`
钉住它（把实现退回位置匹配，**只有那一条**变红）。

⚠️ **`vec_state.content_hash` 的「快速路径」已废弃（2026-10-26 推演证伪）**：原设想是
「整篇 hash 相等就跳过」，但它**永不命中** —— `mark_pending` 会把 `content_hash` 清空，
而 worker 只处理 `pending` / `failed` 的文档，于是 worker 看到的这个字段**恒为 None**。
写它就是一段永不执行的死代码，还会让后人以为「hash 一致就能跳过」是一条生效中的优化。
现在它**只写不读**（状态展示、将来批量对账用），增量判据只有块级 `text_hash` 一处。

### 4.5 后台 worker 的纪律：三条留、两条砍

先按通用做法列了五条（高频写入系统的标配），然后拿本库的**逐版 mtime 统计**去筛 ——
判据是**「这个机制要防的那件事，在 LiMo 的库上会不会发生」**。
那组实测（150 个文档目录 / 316 个版本文件 / **55 条间隔样本**，来自 26 篇有 ≥2 版的文档；
只看文件名与 mtime、不读正文，脚本 [_experiments/04-library-profile/profile_mtime.py](../_experiments/04-library-profile/profile_mtime.py)）的读数是：
同 mode 相邻版本间隔 **>1 天的占 53%（中位 5.0 天）**，<1 小时的只占 29%（中位 3 分钟），
单篇活跃跨度 p50 **5.3 天** —— 典型的「低频、天级、长尾」库。
⚠️ **55 条样本很小**，够支撑「天级」这个量级，不足以谈精确分布（per-doc 中位 5.5 天，
与 pooled 的 5.0 天同量级）。

| 纪律 | 值 | 为什么 | 本库画像下 |
|---|---|---|---|
| **批量编码** | 一次 64 块 | 吞吐比逐条高 3–5 倍 | ⚠️ **留下，但实现按「每篇一次 `embed()`」而非跨篇拼 64 块**（详见 §4.7）：引擎内部已按 DashScope 的 10 条硬上限分批，「篇」是最自然的 checkpoint 边界 |
| **落 checkpoint** | 每批一次 | 关应用 / 断电 / Ctrl+C 不能丢已完成 | ✅ **留**：首次全量本身要跑一小时以上 |
| **失败上限** | 连续 3 篇 | 到上限停 + 界面提示「向量索引已暂停：N 篇编码失败」，不无限重试 | ✅ **留**：这不是性能优化，是失败显式化 |
| ~~**debounce**~~ | ~~30 秒 / 3 秒~~ | ~~连续改五篇只启动一次~~ | ❌ **砍**：版本间隔中位 5 天、>1 天的占 53%，一天改五篇在库上根本不发生。真发生了，一次多花几毛钱 |
| ~~**积压阈值**~~ | ~~pending ≥ 50%~~ | ~~超阈值显示进度条~~ | ❌ **砍掉阈值，留下状态**：不需要「超阈值才显示」，**永远显示** `128/131 篇 · 3 篇失败（重试）` |

**砍掉的那两条是这次最有用的产出** —— 它们不是「忘了做」，是**做过又删了**。
通用做法在这里的失效形态不是「多写了 20 行」，而是**给一个不存在的场景写了一套状态机**：
debounce 需要维护「最后一次写入时间」，积压阈值需要维护「总数」，两个计数器都不会被触发，
但每个读代码的人都要先理解它们，然后才能发现它们是空的。

⚠️ **积压时不要自动降级成「跳过向量、只用字面」** —— 那是静默降级，用户会以为检索坏了。

⚠️ **失败必须显式**：静默跳过的失效形态最糟 —— 用户以为索引是完整的，实际有 30 篇没进去，
而搜索时看不出来。单篇失败不阻塞其他篇，但状态必须落在 `vec_state` 里供状态区展示。

⚠️ **`fail_count` 不只是统计字段，它是「花钱的闸门」**（2026-10-26 补）：LiMo 此前所有重试都是
免费的（字面索引重跑 = 几秒 CPU），而向量重试**每一次都是一次计费调用**。一篇格式怪异的文档
如果陷入重试循环，可以无限烧钱。故三条都是硬要求：
① `fail_count` **持久化**（只在内存里的话，重启即归零 ⇒ 无限重试）；
② 每失败一次**真的 +1**（不是「记了但没读」）；
③ 到上限**真的停**（不是日志里说停了、下一轮又跑）。

⚠️ **留的三条别跟着一起砍**：它们防的事（首次全量太慢、跑到一半断电、失败无声）**在低频库里反而更可能发生**
—— 因为唯一的「高频时刻」就是首次开启那一刻，58 万块要跑一小时。

### 4.6 对账 ≠ 重建

**对账**（启动时或每周一次）：

```
① vec_chunks 里有、文档表里没有 → 孤儿行，删掉
② 文档表里有、vec_state 里没有 → 漏标的，补 pending
③ vec_state.status='failed' 且 fail_count < 3 → 重新排队
```

⚠️ **① 是兜底，不是主要手段**（2026-10-26 审查 P1-01 补）：删除文档时 `routers/ingest.py::_drop_vectors`
**已经即时清** `vec_chunks` + `vec_state`（单删与批量删两条路径）。别把「对账会清孤儿」读成
「删除路径不用管」—— 对账只在 worker 循环**开始时**跑一次，桌面应用能开着好几天；那期间
孤块会继续参与融合、挤占 `depth` 名额，用户点进去发现文档不存在，而设置页那句「删除文档时
对应的向量也会一并清掉」是当面承诺。对账真正的价值是**崩溃 / 半途失败的残留**。

**对账和重建的分工要说死**：对账是「找出漏的补上」，重建是「推倒重来」。
把重建当日常兜底，等于用高成本掩盖增量的漏写 —— 问题还在，只是看不见了。

⚠️ **③ 的实现位置刻意不在 `reconcile` 里**（2026-10-26 落地时定）：它由 worker 的
`run_once` 通过 `retry_ids(max_fail)` 直接消费 —— 状态本来就是 `failed`，取出来重试即可。
若在 `reconcile` 里把它改回 `pending`，`mark_pending` 的语义会**把 `fail_count` 归零**，
于是「已经花过三次钱仍然失败」的记录被抹掉，闸门永久失效。`test_vector_worker.py::
test_reconcile_does_not_reset_fail_count` 钉住这条。

### 4.7 阶段 2 第 3 步已落地（2026-10-26）：后台 worker

`app/services/vector_worker.py`（新）+ `main.py` 挂载 + `DEFAULT_CONFIG["search"]`。

| 落点 | 内容 |
|---|---|
| `VectorWorker.run_once()` | 推一轮队列：先 `take_pending`，不够再 `retry_ids`；单篇失败只 `mark_failed` 不中断；**连续 3 篇失败即停本轮** |
| `VectorWorker._index_one()` | `search_index_text` → `chunk_flat(200)` → 与旧块**按 hash** 比对 → 只编码变了的 → `replace_chunks`（原子整体替换）→ `mark_ok` |
| `VectorWorker.reconcile()` | §4.6 的 ①②，**③ 不在这里**（理由见上） |
| `VectorWorker.loop()` | 启动先对账一次；之后「有进展立刻继续 / 队列空等 60s（**2026-10-27 起：等待期间被写点唤醒即立刻重新判闸门**）/ 被闸门 halt 等 300s」。⚠️ **攒批闸门（§4.2.1）在 `run_once` 之前**，`manual` 档下这个循环只在「立即建立索引」时才真的干活 |
| `DEFAULT_CONFIG["search"]` | `vector_enabled: False`（默认关 = 零回归）/ `vector_model: "dashscope-embedding"` |
| `main.py` startup | enabled 时取引擎 → `ensure_identity` 校验四元组 → 不符则 `note_error`（**不自动重建**）→ 一致才 `create_task(loop)` |
| `main.py` shutdown（新） | `stop.set()` + `task.cancel()`：`set()` 让循环在下一个等待点退出，`cancel()` 兜住「正卡在一次 60s 的 embedding 往返里」 |

**三处与设计原文不同，都是实现时才看清的：**

1. **checkpoint 的粒度比「每批一次」更细** —— 每篇 `mark_ok` 落盘。本篇的块与状态在
   同一个事务里写完，所以「哪篇完成」本身就是最精确的进度单位，不需要另建批次记录。
2. **`attempted` 集合是必需的（不加就是死循环）** —— 失败但未到上限的篇目在下一批
   `retry_ids` 里**仍然会出现**，不挡掉就会在同一轮里反复重试同一篇：一个看上去在推进、
   实际在烧钱的 worker。`test_failed_doc_is_not_retried_within_one_run` 钉住。
3. **失败上限有两个机制，缺一不可** —— 逐篇 `fail_count ≥ 3` 永久放弃（跨轮次，落盘）
   ＋ 本轮「连续 3 篇失败即停」（一次性外部故障：Key 过期 / 断网）。前者防单篇毒药文档，
   后者防把整库均匀烧一遍。

⚠️ **默认关不只是「谨慎」**：打开意味着后台把**全库正文**送去做云端编码。这不是
「多花几毛钱」，是 §5 记的那条隐私面变更 —— 所以它必须由用户显式打开，且开启前的
估算弹窗（阶段 4 的 UI）要把这件事复述一次。

## 五、开关与成本

**默认关闭**，理由与产物侧 `web_search` 同一条纪律：**默认值必须等于改造前的行为**。

开启代价：
- 首次全库 131 篇 ≈ **2 元 / 3 分钟**（实测）；用户库更大则线性增长 → 开启前应展示估算
- 每篇新导入一次 embedding（短文档可忽略）
- ⚠️ **成本按「块数」算，不按「篇数」算 —— 长文档库会放大 5 倍**（2026-10-26 实测）：
  T2Retrieval 的 118,605 篇按 200 字切块后是 **580,701 块（4.9 倍）**，
  本地 `bge-small` 编码 **107 分钟**（6400.7 秒 = 90.7 块/秒；118,605 篇 = 18.5 篇/秒）；
  而同规模的电商集（p50 只有 31 字）是 1 倍。所以「估算弹窗」不能只问篇数，
  得先按语料的 p50/p90 估块数 —— 否则一个以长文为主的库会拿到低 5 倍的报价。
  判据见 `_experiments/03-public-datasets/README.md`（同一套切块参数与模型）。
  ⚠️ **这一条的数字是本地 ONNX 耗时，不是云端 API 耗时** —— 它证明的是「块数」这个
  成本单位会随文档长度放大，不是「云端要跑 107 分钟」。
- ⚠️ **隐私面是新增的，而且量与以前不是一回事**：开启等于把**全库正文一次性发给云端
  embedding 服务**。此前只有用户主动生成某一篇时，那一篇才发给 LLM；这是**全库全量**。
  两项都要做到：① 开关的说明文案写明这一点；② 开启前的估算弹窗里复述一次
  （只写在文档里等于没写 —— 用户看不到）。**本地引擎（阶段 4，2026-10-26 落地）是这条的
  替代路径**：切过去之后内容只在本机编码，设置页文案随之改成「不上传、不计费」。

**不引入降级链**（引擎绑定只取第一个，失败直接报错），与现有引擎语义一致。

**已落地（2026-10-26）**：配置在 `DEFAULT_CONFIG["search"]`（`vector_enabled: False` /
`vector_model: "dashscope-embedding"`）；开关走 `POST /api/search/vector`（就地启停 worker
与融合层，返回动作之后的完整状态，省一次往返）。⚠️ **开启本身不花钱** —— 它只是允许 worker
开始编码，真正的成本发生在后台那一轮；所以成本文案写在开关**旁边**而不是藏在一次确认弹窗里。
重建是另一个端点（`POST /api/search/vector/rebuild`），前端带二次确认 —— 那一次是全库重编码。

### 6.1 阶段 4：本地插件的三个「什么时候」

先钉死一件事：**产品语义完全一致，引擎差异不得改变「什么时候触发」**。
触发点（§4.2 那张表）是产品语义（「内容变了就该重算」），不是引擎语义 ——
按引擎分两套的失效形态是「换了引擎之后，某些更新路径悄悄不生效了」。

| 维度 | 云端内置（dashscope） | 本地插件 |
|---|---|---|
| 单次成本 | 按 token 计费 | 0（CPU / 电） |
| 单次延迟 | 100–300 ms（网络往返） | 5–20 ms/块（CPU，batch 更快） |
| 失败形态 | 网络 / 配额 / key 失效 | 模型文件缺失 / 进程崩 / OOM |
| 内存 | 无 | 模型常驻 20–500 MB（看模型） |
| 启动开销 | 0 | 加载模型 3–5 秒（一次性） |
| **触发点** | §4.2 五个写点 | **同一份**，不另建一套 |

#### （1）索引何时建

| 场景 | 动作 |
|---|---|
| 首次 | 用户装好插件后**第一次开启**向量检索 → 全库 `pending` → 后台补 |
| 增量 | 与云端同一条路（§4.4 块级 hash），无第二套实现 |
| 模型文件 | **下载放在「安装插件」时**，不是「开启检索」时 |

⚠️ 模型下载必须挂在安装这一步：安装是用户明确的动作，那时等 30 秒下 22.8MB 是合理的；
挂在「开启检索」上会让人觉得「点了没反应」（而它其实在下模型，进度条还不知道该怎么画）。

#### （2）何时用（模型加载时机）

这是本地独有的问题，三个选项：

| 方案 | 冷启动代价 | 查询延迟 | 问题 |
|---|---|---|---|
| 启动时加载 | +3–5 秒 | 即时 | 拖慢每次冷启动，而多数用户可能没开向量 |
| 首次查询时懒加载 | 0 | 首次查询 +3–5 秒 | 用户会以为程序卡死了 |
| **开启后由 worker 预热** | 0 | 即时 | ✅ 采用 |

**采用第三条**：`pending` 队列非空时，worker 第一次启动就顺带加载模型。
「开启向量检索」这个动作本身必然产生一批 `pending`，所以模型一定会在**第一批**查询之前加载好。

⚠️ **2026-10-26 修订**：加了释放策略（下面（7））后「常驻」不再恒成立 —— `idle` / `immediate`
两档会把模型放掉，且队列空转时也不预热（`_warm` 已挪到「确认有活」之后）。所以上表第三行的
「即时」要按档位读：`never` 恒即时；`idle` 在阈值内即时；`immediate` 的**建库后第一次查询
必然要等载入**。

⚠️ **边界：开启后立刻查询**（`pending` 还没开始处理）/ 被释放后的第一次查询 → 查询侧
按需载入（`_ensure_loaded()`，独立 `LOAD_TIMEOUT = 30.0`）。载入**失败或超时**时给的是
专属文案（「语义模型载入失败（RuntimeError）」/「语义模型载入超时（>30s）」，
不再报成「检索超时」—— 那读起来像网络问题）；成功载入不额外提示，表现就是这一次搜索慢几秒。

#### （3）何时触发

与云端**同一份**触发点（§4.2），同一份攒批闸门（§4.2.1）—— 云端与本地**共用**
`vector_worker` 的 `_should_run`，没有第二份判据。

⚠️ **没有 debounce 这个参数可改** —— 它在 §4.5 已被砍掉
（本库版本间隔中位 5 天、>1 天的占 53%，一天改五篇的场景不存在）。
⚠️ 攒批阈值（`vector_threshold`）**不是 debounce 的变体**：它按**篇数**攒，与时间无关，
且它防的是「为几篇反复加载本地模型」，对云端引擎只是顺带少几次往返。

零成本还让本地可以多做两件云端该谨慎的事：

- 「生成完成」事件上**立即排队**（写点叫醒 worker，不必等心跳）
- 冷启动对账时把全部 `failed` 重排（云端要谨慎 —— 那是真金白银）

⚠️ **但不要因此省掉 batch**：那是吞吐问题不是成本问题，逐条编码比 batch 慢 3–5 倍。

#### （4）进程外带来的两个后果 —— **2026-10-27 已实现**（`_PluginEmbeddingAdapter`）

`EnginePlugin v1` 默认进程外，对 embedding 有三处影响：

- ✅ **好**：模型崩了不拖垮主进程；依赖隔离（ONNX / torch 版本冲突不波及核心）
- ⚠️ **代价**：每次编码一次 IPC（batch 64 块 ≈ 13 KB 文本 + 130 KB 向量，可接受）
- ⚠️ **必须常驻**：插件进程生命周期 = 应用生命周期，**不能每次编码重载模型**（3–5 秒/次）。
  探测到僵死 → 重启一次；连续崩 3 次 → 停用 + 显式提示（同 §4.5 的失败上限语义）

落地形态是**常驻子进程 + NDJSON over stdio**（不是每次 `Popen`，也不是一次一进程）：
启动握手 `{"ready":…,"dimension":…}` → 每次 `{"id","texts"}` / `{"id","vectors"}` 一问一答。
`id` 错位或非 JSON 行视为管道损坏（杀进程重来），单条 `error` 只报错不杀进程 ——
这两类失败的**下一步动作不同**。协议表与三条硬要求（`-u`、flush、stdout 只写协议行）见
[plugins.md](plugins.md#常驻子进程协议进程外模式)。

**查询侧的分工**：IPC 只用来拿 **query 向量**，余弦由主进程在 sqlite 读出的矩阵上算。
不把整个向量库搬进插件进程 —— 那会让每次查询都传几十 MB。

#### （5）本地插件落地时的依赖归属

`onnxruntime` / `tokenizers` **继续不进 `pyproject.toml`**（现有纪律，见 §七），
装在插件自己的 venv 里。核心只认 `EmbeddingEngine` 协议，不知道对面是云端还是 ONNX。

#### （6）落地形态：内置引擎（2026-10-26）+ 进程外插件版（2026-10-27）

上面（1）–（5）写的是「进程外插件」的设想。**第一版落成了「进程内引擎 + 惰性重依赖」**，
当时给了三条理由；2026-10-27 补了 `EmbeddingPlugin` 基类与 `local_embedding` 插件模板后，
前两条不再是拦路石 —— 现在是**内置与插件并存**（插件同名覆盖内置，见 §7）。

| 当时那条理由 | 现在 |
|---|---|
| ① **签名形状不对**：`EnginePlugin.execute(file_path)` 是「一个文件 → 一段文本」，装不下「一组文本 → 一组向量」 | **已解决**：`EmbeddingPlugin` 是 `EnginePlugin` 的**子类**（扫描 / 门控 / 启用 / 卸载 / 一键装依赖全部复用），只把入口换成 `embed(texts)` |
| ② **进程外救不了查询侧**：预热只解决 worker，而 `fuse()` 的 query 编码每次都要跨进程，`QUERY_TIMEOUT = 3.0` 装不下一次 `Popen` + 模型加载 | **已解决**：进程外 embedding 是**常驻子进程**（NDJSON over stdio 一问一答），不再是每次 `Popen`。查询侧只多一次管道往返（毫秒级） |
| ③ **口子原则的实质已满足**：`onnxruntime` / `tokenizers` 不进 `pyproject.toml`，模型不随包 | **仍成立，但只覆盖源码版**：打包版的主环境是冻结的 exe，用户补不了这两个包 —— 所以要的不是「重依赖不进包」，而是「**能让用户自己补**」，这一条只有插件能给 |

**于是两者分工**：

- **源码版**：内置引擎零安装可用（`pip install onnxruntime tokenizers` + 模型文件即可）
- **打包版**：内置那份缺依赖时，`precheck` 会指两条路 —— 云端，或**装 `local_embedding` 插件**
  （插件带自己的 venv，依赖装得进去）。装了之后同名覆盖内置，下拉里只剩插件那条，
  且 `model_id` / 维度 / 模型目录与内置完全一致 ⇒ **向量库不必重建**
- **内置那份仍然保留**：它不是插件的备份，而是「源码运行的零安装路径」；删掉它等于让
  每个源码用户先去装插件

插件侧契约（常驻协议、`-u`、`LIMO_PLUGIN_CONFIG`、`requires_modules` 与 `probe_venv` 的分工）
见 [plugins.md](plugins.md#向量化插件embeddingplugin-v1)。

| 项 | 云端 `dashscope-embedding` | 本地 `local-bge-small` |
|---|---|---|
| 维度 / `modelId` | 1024 / `text-embedding-v4` | **512** / `bge-small-zh-v1.5-int8` |
| 单条输入上限 | 8192 token | **512 token ≈ 400–500 中文字** |
| 切块 | `DEFAULT_CHUNK_SIZE = 200` 字 | **同一份**（正好落在本地能力内） |
| 成本 | 按字数计费 | 0（CPU） |
| 使用条件 | 只需 API Key | **需自备依赖 + 模型文件；源码版可 pip 补，安装版靠插件版** |
| 代价 | 全库正文外发 | 首次加载 3–5 秒 + CPU 占一段时间 |

⚠️ **「使用条件」对所有用户可见、不静默**（2026-10-26 用户拍板：不做内置、不做插件，
但必须说清楚）。`precheck()` 的文案分两档：

- **源码模式**：镜像源的 `pip install` + 模型文件落点 +「补齐后重启应用生效」——
  最后半句不是客套，`find_spec` 查的是**当前进程**的 `sys.path`，装完不重启就看不见新包，
  界面上会继续显示「缺依赖」，像没装上。
- **`sys.frozen`（打包版）**：**直说应用内补不了**并给出路（改用云端，或装本地向量化插件）。
  这不是措辞问题 —— `LiMoBackend.exe` 跑在冻结的 Python 里**没有 pip**，用户机器上通常也没有
  第二个 Python，给一条跑不了的命令比不给更糟（用户会以为是自己操作错了、反复试）。
  ⚠️ **只说云端是不够的**（2026-10-27 修）：那会让人以为离线选项在安装版上不存在，
  而装一次 `local_embedding` 插件之后本地能力一样有。

设置页一侧，「选中引擎未就绪」的原因**常驻显示**（`SearchIndexCard` 的 `data-vector-requirement`）：
`vector_enabled=false` 时 `sync_vector_runtime` 的 reason 恒为 `None`，只靠那段用户
**得先去点一下下拉**才知道自己选的引擎用不了。

⚠️ **`int8` 必须写进 `modelId`**：它与 fp32 的向量不完全相同，共用一个 id 时
`ensure_identity` 会判「没变」而实际向量已换 —— 检索质量轻微下降、零报错。

**三个可选钩子**（不进 `EmbeddingEngine` Protocol —— `runtime_checkable` 加成员会让
云端引擎不再满足，消费方一律 `getattr`）：

- `precheck() -> str | None`：就绪自检（依赖装没装 / 模型文件在不在），**排在
  `ensure_identity` 之前**。反过来写会把四元组身份先写成新口径，于是「装完依赖回来」
  看到的是「口径不符，需要重建」，而其实一个向量都还没编码过。
- `warmup()`：worker 每轮开跑前调一次（**排在 `_next_ids` 确认有活之后** —— 队列空着时
  加载 22.8MB 纯属浪费）。已加载时是纯内存快路（查询侧每次都会调）。预热失败写
  `stats["stopped"]` 且**不** `mark_failed` —— `fail_count` 是花钱的闸门，模型没起来
  不是这篇文档的错。
- `release(*, after_idle=DEFAULT_IDLE_RELEASE) -> bool`：把模型句柄丢掉并归零计时
  （2026-10-26）。详见下面「（7）模型内存释放」。

**引擎可切换**：`POST /api/search/vector` 的 `model` 字段（非法值 → 400
`VECTOR_NO_ENGINE`，零写盘）；`status.vector` 的 `models` 给 `label` / `dimension` /
`local` / `ready` / `reason`。⚠️ **切引擎不自动重建**：维度 1024 ↔ 512 必然「口径不符」，
后端显式给出原因，重建由用户点（那是花钱的动作）。前端成本文案按 `local` 分支，
**不按名字前缀猜**。

#### （7）模型内存释放（2026-10-26）

建完全库之后那几十 MB 可以还回去。`search.vector_release` 三档，**用户可选**：

| 档 | 行为 | 代价 | 谁消费 |
|---|---|---|---|
| `never` | 一直留着 | 常驻不还 | `maybe_release()` 直接 `False` |
| `idle`（**默认**） | 闲置超阈值就释放 | 日常≈「建完就放」，刚建完顺手搜仍是快的 | `release()`（**不传 `after_idle`**） |
| `immediate` | 建完立刻释放 | 之后第一次搜索等几秒载入 | `release(after_idle=0.0)` |

三条纪律：

1. **阈值住在引擎侧**（`embedding_local.DEFAULT_IDLE_RELEASE = 600.0`），worker 不知道。
   「多久算闲置」是本地引擎的属性；云端根本没有「加载」这回事。`idle` 档调
   `release()` 时**不传 `after_idle`** —— 传了就是第二份判据（前端/worker 各有一份
   「多久算久」的答案）。
2. **`immediate` 只在本轮真有推进后释放一次**（`loop` 里 `if stats["indexed"] or
   stats["failed"]: self._pending_release = True`，`maybe_release()` 消费即复位）。
   空转也释放的话，用户刚搜过、模型刚载进内存，一轮空转就把它踢掉 —— 现象是「明明刚用过，
   下一次搜索又要等几秒」，而日志上一切正常。释放后 `_warmed = False`，下一轮走
   `_warm()` 而非每篇惰性加载。
3. **释放后查询侧必须自己把模型载回来**：`VectorSearcher._ensure_loaded()` 在
   `_precheck` 之后、编码之前调 `warmup()`，用**独立的** `LOAD_TIMEOUT = 30.0` 包住。
   ⚠️ **不是放宽 `QUERY_TIMEOUT = 3.0`** —— 那会让「一次查询真的卡住」也干等 30 秒。
   载入超时 / 载入失败各有专属文案，与真正的查询超时分开；失败只降级这一次查询。

**入口严、读回宽**：`POST /api/search/vector` 的非法 `release` → 400
`VECTOR_BAD_RELEASE` 且**零写盘**；`GET /api/search/status` 读配置时对脏值静默回退
`idle`（那是「磁盘上可能过期的值」）。`vector_runtime._ensure_worker` 在**策略变化时
重启 worker** —— 不重启的话配置改了而行为不变，是这一整块最容易出现的静默失效。

## 七、测评方法（改检索前必跑）

### 7.0 门禁层：`bash scripts/check-all search`（2026-10-29）

上面那两个脚本跑的是**真实库**（要有库、要有 `~/.limo`），因此进不了 CI。故另有一层
**离线可跑、约 1 秒**的门禁：

| 件 | 位置 | 是什么 |
|---|---|---|
| 语料快照 | `backend/tests/fixtures/search_eval_corpus.json` | 10 份 md 的 81 条 H2 切片（100–3000 字，剥围栏后计长） |
| 查询集 | `backend/tests/fixtures/search_eval_queries.json` | 30 题（语义 12 / 精确 10 / 混合 8），手写评审 |
| 基线 | `backend/tests/fixtures/search_eval_baseline.json` | `{topk, corpusHash, overall, perKind, ranks}`，实测 `23/30` |
| 生成器 | `backend/scripts/build_search_eval.py` | `--corpus` 重建快照 / `--update-baseline` 写基线 |
| 判据 | `backend/tests/test_search_eval.py` + `eval_search._score` | **打分同源**，只有数据是自己的一份 |

**⚠️ 三条边界，别读成「检索好不好」的结论：**

1. **它测的是字面层**（`SearchEngine.search`），**不含向量与 RRF 融合**，也不含对话侧。
   `VectorSearcher.fuse` 的编排（depth / RRF k / 语义独有回补）**一个字都不会反映到
   分数上** —— 那些由各自的单测守。
2. **绝对分数不可迁移**。切片把 H2 当「一篇文档」（几百到三千字），而真实库里一篇
   transcript 是整段视频转录（上万字）。BM25 的长度归一化让检索单元变小 ⇒ 命中显著更容易
   —— 这正是本项目踩过的 **40pp 落差**形态。**只在同一份语料的前后对比里有意义**，
   不要拿去跟 §2.2 的 29 题真实库分数比。
3. **它用快照而不是现切**。现切的失效形态是「改一句文档 → 语料变 → 基线漂移 → 门禁因
   无关改动变红」。代价是快照会随时间脱节，由 `--corpus` 显式重建承担（重建后**必须**
   同时 `--update-baseline`，基线里存了语料指纹，对不上会直接报错）。

**⚠️ 更新基线必须在 `docs/CHANGELOG.md` 记一句理由。** 否则开发者看到一片红，唯一能干的
就是随手 `--update-baseline`，基线就成了橡皮图章。

自证有区分力：一条负向对照（把每题的目标整体错位一位）—— 实测 `4/30`（基线 `23/30`）。
实测把 `ORDER BY rank` 改成 `ORDER BY id DESC` 时：合计 `10/30`，两个用例同时红并打出
完整掉队清单（哪题、从第几名掉到第几名）。

⚠️ **`check-all all` 里它跑两次**（`pytest` 层也会收集到 `tests/test_search_eval.py`）。
这是刻意的：`search` 层的价值在**失败时那一屏输出**，不在另起一套判据。

### 7.1 真实库评测（29 题）

```bash
cd backend
python scripts/eval_search.py                 # 当前产品判据（含笔记）
python scripts/eval_search.py --mode raw      # 对照：只 rawText
python scripts/eval_search.py --json          # 机器可读
```

29 题人工标注（语义 15 / 精确 9 / 混合 5），判据「目标进前 5」。

`--vector` 加跑**纯向量与 RRF 两路**（`--chunk` / `--chunk-size` / `--rrf-k` / `--depth`
可调）。它需要 `onnxruntime` + `tokenizers`，而这两个**刻意不在 `pyproject.toml` 里** ——
重依赖不进核心打包（阶段 4 的本地引擎同一条纪律，见 §6.1 (6)）；缺失时显式报错并给出

转出口）—— 评测与产品必须指向同一份权重与同一份实现。
**不传 `--vector` 时输出与改造前逐字节相同。**

### 缺一维：陷阱题

现有 29 题**全是「应该有结果」的正向题**，缺「库里根本没有这个话题时返回什么」这一维。
而「搜不到却甩出一堆无关结果」比「搜不到」更伤 —— 用户会以为库里真有。

补法（⚠️ 阶段 1–3 已于 2026-10-26 落地，**这一维仍未补** —— 它是下一轮评测的首要缺口）：
加 5–8 道**库里确定没有答案**的查询，
判据不是「命中」而是「top 1 分数低于阈值」或「前 5 名里没有高相关项」。
阈值要等两路分数都跑出来才定得下来，现在只记这一维缺口，不预设数字。

> ⚠️ 这一步不是可选的。2026-10-26 实测过「单测全绿 + 实验脚本 83% + 产品 41%」三者同时成立，
> 只有拿产品代码跑真实库才能暴露它。

### 公开集复核（改动融合逻辑前后各跑一次）

29 题给的是「在这个库上能不能用」，**给不了「这个策略在别的领域还成不成立」**。
四个公开中文检索集（电商 / 医疗 / 视频 / T2 长文档，各 10 万+ 语料）在
[`_experiments/03-public-datasets/`](../_experiments/03-public-datasets/)，
一条命令跑完并落逐题 rank —— **换判据/换配对组合是纯计算，不用重编码**。

| 要回答的问题 | 用哪个数 |
|---|---|
| 换了之后有没有变差（产品库） | `eval_search.py` 的 Hit@5 + 逐题名次 |
| 是不是只在当前 k / 权重下成立 | `--criteria` + `--rrf-k` / `--rrf-w` 各扫一遍 |
| 差的那几个点是真差还是噪声 | `--bootstrap`（配对，单位是 query） |
| 该改召回还是改排序 | `@5` 与 `@50` 的落差（<60% 命中 ⇒ 召回问题） |
| 换了实现有没有静默漂移 | `diff_ranks.py` 比对改造前后两份 rank |

⚠️ **融合权重不能写死**：四个集上「两路精度差」与「等权收益」是连动的
（差 5pp 时 +3.8，差 15pp 以上是 0 到负），所以 `rrf_weights` 必须可配，
默认等权只在两路精度接近时成立。依据见该目录 README §3 偏差 2。

## 八、未决问题（落地时逐个回答）

1. ~~**规模闸门**：1000 篇 / 1 万篇的真实查询耗时是多少？超过多少要上 HNSW？~~
   → **已回答（2026-10-26，解析推算）**：拐点在 **50 万块 ≈ 5 万篇**（384 维 float32 暴力检索
   100–200 ms）。个人库到不了 ⇒ **不需要 ANN**。追根见 §3.2.2。
   ⚠️ **这个数是按内存带宽与余弦计算量推的，不是实测**。落地时若真接近 5 万篇需重新测量。
2. ~~**RRF 的 k**：29 题上 k=10 最好，更大集合上是否仍如此？~~
   → **已回答（2026-10-26）**：1000 题上 k=10 仍最好（10 > 20 > 60 > 100，单调）。
   ⚠️ **但 k 与权重耦合**：一旦给字面加权（3:1），k=60 反超 k=10 —— 因为 k 小会放大
   「某一路排第 1」的权威性，而低精度那一路的第 1 名经常是错的。
   **两根旋钮必须一起调**（这也是第 6 条 rerank 的前置）。
3. **查询向量缓存**：常用查询要不要缓存 embedding？缓存失效策略是什么？
   ⚠️ **它的安全面从没被讨论过，而它比索引本身更敏感**：文档正文进索引是「用户自己要存的东西」，
   而**查询词是用户正在想什么** —— 一份查询缓存就是一份「搜索意图日志」（含他没点开的那几条）。
   落地时三条底线：① 落在 `~/.limo` 之外不成立（那目录会被同步/打包分享），按现有约定进
   `%LOCALAPPDATA%`；② 有 TTL 与条数上限，不能像已删除的 `store.cache_put` 那样**永不清理**；
   ③ 关掉检索开关时缓存要一起清 —— 否则「我关了向量检索」之后，历史查询词还躺在磁盘上。
   **更要紧的一条**：如果将来做「查询建议 / 热门搜索」，那是把这份日志**展示**出来，
   必须显式开关 + 明确告知，不能默认开。
4. **摘要用哪一路**：融合结果里字面命中给 snippet，纯向量命中给什么？（可能给块文本）
5. ~~**本地插件的三个「什么时候」**：索引何时建 / 何时用 / 何时触发~~
   → **已回答（2026-10-26）**：见 §6.1。三条分别是「装插件时下模型、开启时全库 pending」
   /「worker 预热加载、常驻、不重载」/「与云端同一份触发点，没有 debounce 可改」。
6. **重排要不要上**：RRF 之后如果仍不够，上 rerank（dashscope 有现成模型）；届时
   「召回多少条送进精排」与 `k` 一起调，不能只调一个。
7. ~~**切块策略本身的收益有多大**~~ → **已回答（2026-10-26）**：固定字数切 200 字最好（RRF 93%），
   H2 语义切 + 前置标题在各档都没跑赢（90%）。详见 §3.2 的表。
   ⚠️ **但落地时仍要做成可切换的** —— 这个结论绑定在 `bge-small`（512 token）上，
   换成云端 v4（2000 字符）或别的模型必须重跑。而且「H2 切但不加标题」的消融**还没做**，
   所以「为什么 H2 切更差」目前只有推测。
8. **`vec_state` 剩下的两个数还是拍的**：批量 64 块、失败上限 3 篇 —— 两条**工程经验值，
   都没有实测支撑**（debounce 与积压阈值已在 §4.5 按 mtime 实测砍掉，那两个数有依据了）。
   落地后要拿真实使用日志（单次编辑影响的块数分布、失败重试的成功率）回头校准，
   否则它们会和 `MAX_NEW_FOLDERS = 5` 一样成为「看起来有依据」的魔数。
