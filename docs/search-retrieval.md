## 一、现状：字面检索（已落地）

```
写入侧                                    查询侧
──────                                    ──────
update_index(engine, store, tx_id)        search(query, limit)
  ↓ 判据：doc_text.search_index_text        ↓ _tokenize(query, limit=64)
rawText + 最新版笔记                        ↓  CJK 二字组 + 英文词 + 数字串
  ↓ _clean_for_search（不分词、不截断）      ↓ _escape_fts5 → OR 连接
  ↓ _tokenize（不封顶）                     ↓ FTS5 MATCH ... ORDER BY rank (BM25)
{title, body(UNINDEXED), toks} 三列         ↓ _make_snippet（从 body 取原文）
```

### 三条不能动的判据

| 判据 | 为什么 |
|---|---|
| `_tokenize` 的 `limit` 默认 **None** | 索引侧必须收全文。曾经无条件 `uniq[:64]`，每篇只索引开头 64 个 token，而所有单测都是短文本、全绿 |
| 查询用 **OR** 不是 AND | 二字组 AND = 一票否决，语义型查询归零（15 题 7→0） |
| `body` 列 **UNINDEXED** | 摘要是给人看的。token 化是检索的内部表示，不能泄漏到展示层 |

### 五个写点

摄入 / 重新转录 / 生成完成 / 编辑保存 / 启动重建 —— 全部经 `update_index()`，
内容判据只有 `search_index_text` 一处。

## 二、向量检索：为什么做

### 2.1 先回答「我们的数据属于哪一类」

业界判断「该不该上向量」的常用判据不是复杂度，是**数据结构化程度**：

| 维度 | 非结构化（法律文档 / 知识库） | 结构化（代码库） |
|---|---|---|
| 检索方式 | 语义匹配，找同义词近似词 | 字面精确，错一个字就匹配不上 |
| 变化频率 | 几年才变 | 经常变 |
| 索引维护 | 变更少，成本低 | 每变一次都要重建 |
| 适合方案 | 传统 RAG / embedding | grep / BM25 / Agentic Search |

Claude Code 落在右边那一列，所以它用 grep 而不是 RAG —— **这是数据形态决定的，不是路线之争**。

LiMo 的文档库落在**左边**那一列：视频转写、网页、论文、个人笔记，全是自然语言；
而且导入后基本不再变（比「几年才变的法律文档」更稳定）。**索引维护成本在我们的场景里趋近于零**，
这恰恰是 Claude Code 拒绝传统 RAG 的那条理由在我们身上不成立。

⚠️ **但两者的检索入口形态也不同，这一点不能忽略**：Claude Code 的检索发生在 **agent loop 里**
（可多轮改写查询），而 LiMo 的搜索框是**单轮、250ms 消抖、要求即时**——没有 agentic 多轮试探的余地。
Boris 那句权衡 `Agentic search can outperform RAG, but at the cost of latency and tokens` 里的
「at the cost of latency」正是我们这个入口付不起的东西。
（对话侧那条是 agent loop，它走的是 `search_docs` 工具，与搜索框是两条路径。）

### 2.2 29 题实测

29 题实测，两路失手题**几乎完全错开**：

| | 失手（131 篇库） |
|---|---|
| 字面（83%） | 4 道纯语义改写 + `1048` |
| 向量（86%） | 3 道专有名词 + `1048` |
| **交集** | **仅 `1048`**（数字规范化问题，与检索方式无关） |

RRF 融合上限 **97%**（k=10，等权）。

**本地模型也是同一结论**（`bge-small-zh-v1.5` ONNX int8，22.8MB，CPU，零 torch）：
137 篇库上纯向量 83%、RRF **93%**，字面基线 79%。**相对排序与云端那轮完全一致。**

| | 纯向量 | RRF(k=10) | 成本 | 外发 |
|---|---|---|---|---|
| 云端 `text-embedding-v4` | 86% | **97%** | ~2 元/次全量 | 全库正文出网 |
| 本地 bge-small int8 | 83% | **93%** | 0 | 零 |

> ⚠️ **跨轮数字不能直接比**：云端那轮 131 篇 / 基线 83%，本地这轮 137 篇 / 基线 79%。
> 「97% vs 93%」里混着分母变化，**不能读成「云端模型更好」**。

> ✅ **两组数都能独立复现，且不依赖 `_experiments/`**（2026-10-26 补 `--vector`）：
> `python scripts/eval_search.py --vector` 直接打出字面 / 纯向量 / RRF 三路，137 篇库上
> 复现 **79% / 83% / 93%**，**逐题失手清单与原实验逐条一致**。
> 实验脚本 `_experiments/02-embedding-rrf/eval_ab.py` 仍保留（它做「多切块策略扫描」，
> 产品脚本不做那件事），但两边的 `Embedder` / 切块 / `rrf` 已收编成同一份
> `backend/scripts/embed_local.py` —— 各自抄一份正是
> [01-lexical-search](../../_experiments/01-lexical-search/README.md) 里那 40pp 落差的成因。

> ⚠️ **29 题样本小**，1 题 = 3.4pp，97% 的置信区间很宽，k=10 也未必是最优
> （实测 k=60 是 90%，与业界默认相反 —— 因为一路第 1、另一路很差时会被拉平）。
> 落地时保留 `k` 可配。

> 🔬 **已在公开数据集上复核（2026-10-26，`mteb/EcomRetrieval`，10 万条 × 1000 题）**：
> 详见 [_experiments/03-public-datasets/](../../_experiments/03-public-datasets/README.md)。
> 三条结论，两打折一条成立：
>
> | 结论 | 在 1000 题上 |
> |---|---|
> | 向量 > 字面 | ✅ 成立，且差距更大（64.2% vs 49.1%，+15.1pp） |
> | 融合有收益 | ⚠️ **量级缩小一个数量级**：+1.7pp（1:2）/ +0.1pp（等权），而这里 +10pp |
> | **RRF 等权优于加权** | ❌ **被推翻**：等权次优，最优是 `字面:向量 = 1:2`；且等权的 nDCG/MRR **低于纯向量** |
> | k=10 优于 k=60 | ✅ 原样成立 |
>
> **为什么融合的收益差 10 倍**：RRF 等权隐含「两路排名同等可信」。这里两路精度 79% / 83%（差 4pp）
> 且失手几乎不重叠（交集仅 1 道）⇒ 假设成立；Ecom 上是 49% / 64%（差 **15pp**）⇒
> 给低精度信号一半话语权的直接后果就是排序指标下降。
> **所以落地时权重不能写死等权**，而且 `k` 与权重是**耦合**的（给字面加权后 k=60 反超 k=10）。
>
> ⚠️ **Ecom 测不到切块与长文档聚合**（一条商品标题就是一块），它复核的是「检索方案」这一个变量。
> 这不推翻上面那两张表（那些是在 LiMo 自己的库上测的），它给出的是**适用边界**。

> ⚠️ **这是「一次性检索 vs 一次性检索」的对比**，不能拿去跟 agentic 方案比 ——
> 有公开实验显示 agentic + 纯 BM25 可以打败一次性 embedding 切块检索（代价是延迟与 token）。
> 这不推翻本计划（我们的入口没有 loop 的余地，见 2.1），但引用这个数字时必须带上限定。

> ⚠️ **切块上限是模型能力的硬约束，不是可调参数**。`bge-small` 的 `max_length` 是
> 512 token ≈ 400–500 中文字，照搬云端的 2000 字符会让后半段被 tokenizer **静默截断** ——
> 实测 1000 字符块只有 76%，比不做向量（79%）还低。见 §3.2。

## 三、架构：引擎 + 存储 + 融合层

### 3.1 EmbeddingEngine（新增引擎类别）

与 OCR / ASR / Doc 同款，注册进 `EngineRegistry`：

```python
class EmbeddingEngine(Protocol):
    name: str                      # 展示名
    model_id: str                  # 落库用于失效判定（换模型 = 全量重建）
    dimension: int
    async def embed(self, texts: list[str]) -> list[list[float]]
```

**内置 `dashscope-embedding`**（`text-embedding-v4`）：
- 走已有的 dashscope provider key + OpenAI 兼容端点，**核心零新依赖**
- 判据来自「口子原则」四标准：依赖不重、无协议问题、跨平台无碍、无法律风险 → **留核心**
- 这是它与 whisper（CUDA）/ tesseract（280M）/ docling（torch 2GB）的区别 ——
  那三个是因为重才出核心，云端 embedding 不重

**本地模型走插件口子**（`EnginePlugin v1`）：bge-m3 / ollama 等 1–2GB 依赖、有 CPU/GPU 差异 → 插件化。
⚠️ **本地插件的索引时机 / 触发方式 / 使用时机（何时建、何时用、增量还是全量）留待后续详细设计**，
本阶段只保证引擎接口能容纳它，不实现加载路径。

### 3.2 向量存储

与字面索引**同库不同表**（`{data_dir}/search.db`）：

```sql
CREATE TABLE vec_meta (            -- 单行，记录本库向量的"身份"
    model_id TEXT,                 -- 换模型 → 整库失效
    dimension INTEGER,
    chunk_size INTEGER,
    built_at TEXT
);
CREATE TABLE vec_chunks (
    tx_id TEXT, chunk_idx INTEGER,
    text TEXT,                     -- 原文分块（摘要/调试用）
    vec BLOB,                      -- float32 打包
    PRIMARY KEY (tx_id, chunk_idx)
);
```

- **文档得分 = 各块余弦最大值**（不是平均 —— 平均会稀释「只有一段相关」的长文档）
- ⚠️ **切块策略已 A/B，结论与原设计相反**（2026-10-26，137 篇，RRF k=10）：

  | 策略 | 纯向量 | +RRF | 块数 | 编码 |
  |---|---|---|---|---|
  | **固定切 200 字** | 83% | **93%** | 6561 | 29.4s |
  | 固定切 400 字 | 83% | 90% | 3960 | 39.0s |
  | H2 切 400 + 前置标题 | 79% | 90% | 4404 | 47.9s |
  | H2 切 1000 + 前置标题 | **76%** | 90% | 2477 | 49.3s |

  **默认用固定字数切（按 `\n\n` 段落累积，不切断段落），不按 H2 切。**
  原设计是「H2 语义边界 + 块前置标题」，实测没跑赢 —— H2 切会把文档切成长度极不均匀的块
  （有的小节 50 字、有的 2000 字），而余弦相似度在**长度相近**的文本间比较才稳定。
  ⚠️ 这个解释**还没做消融验证**（需要「H2 切但不加标题」一组），所以是推测不是结论。
- ⚠️ **切块上限由模型 `max_length` 倒推，不能照抄**：`bge-small` 是 **512 token ≈ 400–500 中文字**。
  原设计写的「H2 内超过 1000 字符再切」会让后半段被 tokenizer **静默截断** ——
  不报错、块看起来完整，只是那半段永远搜不到（实测 76%，比不做向量还低）。
  那个阈值是给 `bge-m3`（8192 token）写的。**换模型必须重算这个数。**
- ⚠️ **表格单独处理**：表格被切碎后每一行都失去表头，向量会读成毫无意义的短句。
  至少保证「表头 + 若干行」留在同一块内（产物里的 `table` 块有 `limo-block` 围栏可用来定位）
- ⚠️ **规模闸门**：137 篇固定切 200 = **6561 块**，纯 Python + numpy 全量余弦可接受（30 秒建库）；
  但 1 万篇 ≈ 50 万块，需要 `sqlite-vec` 或 HNSW 之类。**落地时先测 1000 篇的真实耗时再决定**，
  不提前引入依赖。

### 3.3 融合层

```
query ──┬─→ 字面 search()             → [id...] （top 50）
        └─→ embed(query) → 余弦        → [id...] （top 50）
                                        ↓
                              RRF: score = Σ 1/(k + rank)   k=10
                                        ↓
                                   最终 top N
```

只用排名不用分数 —— BM25 与余弦量纲不可比，归一化会引入新超参。

**为什么先 RRF、不先 rerank**：两者解决的是同一个问题（把对的排前面）。RRF 零模型零成本、纯本地排序；
rerank 是第二个模型调用（每次查询都花钱 + 增加延迟）。先用 RRF 拿基线，实测仍不够再上 rerank——
但**它是明确的后备选项，不是没想到**。

⚠️ **两者能救的不是同一批题**：RRF 只重排「两路都召回了的东西」，一路召不回的正确文档它救不了；
rerank 是在**已有候选集内部**精排，收益上限取决于候选集里有没有正确答案。
所以真上 rerank 时，「召回多少条去精排」与 `k` 必须一起调 —— 只调一个，数字会好看得莫名其妙或难看得知其所以然。

## 四、索引时机（云端内置这一支必须先定）

字面索引是**同步、无成本、必成功**的；embedding 是**异步、有 API 成本、可能失败**的。
两者不能塞进同一个同步路径。

### 4.1 写入：字面先落，向量后补

```
update_index()                        ← 五个写点共用，行为不变（同步，快）
  ├─ 字面索引（现有）
  └─ 标记该篇「向量待更新」（vec_chunks 删除 + 待办表记一行）

后台任务（异步）                        ← 新增，独立循环
  ├─ 取待办 → 分块 → engine.embed() → 写 vec_chunks
  ├─ 失败：留痕 + 重试计数，**字面检索不受影响**
  └─ 引擎不可用 / 未开启：整批跳过，状态显式可见
```

**为什么不阻塞写入**：生成/编辑的响应时间不该被一次 embedding 网络往返拖慢；
而字面检索已经 79–83%，向量只是增量收益 —— 慢一步可用，强过卡住主流程。

⚠️ 但这违反「失败显式化」吗？不违反，**前提是状态可见**：设置页显示
「向量索引：128/131 篇 · 3 篇失败（重试）」，而不是静默只索引了 128 篇。

### 4.2 触发点

| 时机 | 动作 |
|---|---|
| 用户开启向量检索 | 全库标记待更新 + 后台批量补（进度可见） |
| 五个写点任一触发 | 该篇标记待更新 |
| 换 embedding 模型 | `vec_meta.model_id` 不匹配 → **整库失效重建**（旧向量维度可能不同，不能混用） |
| 用户关闭向量检索 | 后台任务停；**数据保留不删**（重新开启不必重算） |
| 启动时 | 补跑上次未完成的待办（与字面索引的启动重建同一次机会） |

### 4.3 查询：embedding 失败怎么办

- 查询 embed 失败 → **退化为纯字面**，结果照给，但 UI 要显示一行「语义检索暂不可用」
- ⚠️ 不能静默退化：用户会以为「向量没帮上忙」，实际是「向量压根没跑」

## 五、开关与成本

**默认关闭**，理由与产物侧 `web_search` 同一条纪律：**默认值必须等于改造前的行为**。

开启代价：
- 首次全库 131 篇 ≈ **2 元 / 3 分钟**（实测）；用户库更大则线性增长 → 开启前应展示估算
- 每篇新导入一次 embedding（短文档可忽略）
- ⚠️ **成本按「块数」算，不按「篇数」算 —— 长文档库会放大 5 倍**（2026-10-26 实测）：
  T2Retrieval 的 118,605 篇按 200 字切块后是 **580,701 块（4.9 倍）**，编码 63 分钟；
  而同规模的电商集（p50 只有 31 字）是 1 倍。所以「估算弹窗」不能只问篇数，
  得先按语料的 p50/p90 估块数 —— 否则一个以长文为主的库会拿到低 5 倍的报价。
  判据见 `_experiments/03-public-datasets/README.md`（同一套切块参数与模型）。
- ⚠️ **隐私面是新增的，而且量与以前不是一回事**：开启等于把**全库正文一次性发给云端
  embedding 服务**。此前只有用户主动生成某一篇时，那一篇才发给 LLM；这是**全库全量**。
  两项都要做到：① 开关的说明文案写明这一点；② 开启前的估算弹窗里复述一次
  （只写在文档里等于没写 —— 用户看不到）。本地插件（阶段 4）是这条的唯一替代路径。

**不引入降级链**（引擎绑定只取第一个，失败直接报错），与现有引擎语义一致。

## 七、测评方法（改检索前必跑）

```bash
cd backend
python scripts/eval_search.py                 # 当前产品判据（含笔记）
python scripts/eval_search.py --mode raw      # 对照：只 rawText
python scripts/eval_search.py --json          # 机器可读
```

29 题人工标注（语义 15 / 精确 9 / 混合 5），判据「目标进前 5」。
脚本只读库、索引建在临时目录、判据走产品函数 —— **不在脚本里另拼一份**。

`--vector` 加跑**纯向量与 RRF 两路**（`--chunk` / `--chunk-size` / `--rrf-k` / `--depth`
可调）。它需要 `onnxruntime` + `tokenizers`，而这两个**刻意不在 `pyproject.toml` 里** ——
本地 embedding 走插件口子（阶段 4），不该进核心依赖；缺失时显式报错并给出安装命令，
不静默退化。**不传 `--vector` 时输出与改造前逐字节相同。**

### 缺一维：陷阱题

现有 29 题**全是「应该有结果」的正向题**，缺「库里根本没有这个话题时返回什么」这一维。
而「搜不到却甩出一堆无关结果」比「搜不到」更伤 —— 用户会以为库里真有。

补法（阶段 3 连同 `--vector` 一起做）：加 5–8 道**库里确定没有答案**的查询，
判据不是「命中」而是「top 1 分数低于阈值」或「前 5 名里没有高相关项」。
阈值要等两路分数都跑出来才定得下来，现在只记这一维缺口，不预设数字。

> ⚠️ 这一步不是可选的。2026-10-26 实测过「单测全绿 + 实验脚本 83% + 产品 41%」三者同时成立，
> 只有拿产品代码跑真实库才能暴露它。

### 公开集复核（改动融合逻辑前后各跑一次）

29 题给的是「在这个库上能不能用」，**给不了「这个策略在别的领域还成不成立」**。
四个公开中文检索集（电商 / 医疗 / 视频 / T2 长文档，各 10 万+ 语料）在
[`_experiments/03-public-datasets/`](../_experiments/03-public-datasets/)，
一条命令跑完并落逐题 rank —— **换判据/换配对组合是纯计算，不用重编码**。

| 要回答的问题 | 用哪个数 |
|---|---|
| 换了之后有没有变差（产品库） | `eval_search.py` 的 Hit@5 + 逐题名次 |
| 是不是只在当前 k / 权重下成立 | `--criteria` + `--rrf-k` / `--rrf-w` 各扫一遍 |
| 差的那几个点是真差还是噪声 | `--bootstrap`（配对，单位是 query） |
| 该改召回还是改排序 | `@5` 与 `@50` 的落差（<60% 命中 ⇒ 召回问题） |
| 换了实现有没有静默漂移 | `diff_ranks.py` 比对改造前后两份 rank |

⚠️ **融合权重不能写死**：四个集上「两路精度差」与「等权收益」是连动的
（差 5pp 时 +3.8，差 15pp 以上是 0 到负），所以 `rrf_weights` 必须可配，
默认等权只在两路精度接近时成立。依据见该目录 README §3 偏差 2。

## 八、未决问题（落地时逐个回答）

1. **规模闸门**：1000 篇 / 1 万篇的真实查询耗时是多少？超过多少要上 HNSW？
2. ~~**RRF 的 k**：29 题上 k=10 最好，更大集合上是否仍如此？~~
   → **已回答（2026-10-26）**：1000 题上 k=10 仍最好（10 > 20 > 60 > 100，单调）。
   ⚠️ **但 k 与权重耦合**：一旦给字面加权（3:1），k=60 反超 k=10 —— 因为 k 小会放大
   「某一路排第 1」的权威性，而低精度那一路的第 1 名经常是错的。
   **两根旋钮必须一起调**（这也是第 6 条 rerank 的前置）。
3. **查询向量缓存**：常用查询要不要缓存 embedding？缓存失效策略是什么？
4. **摘要用哪一路**：融合结果里字面命中给 snippet，纯向量命中给什么？（可能给块文本）
5. **本地插件的三个「什么时候」**：索引何时建 / 何时用 / 何时触发 —— 待设计。
6. **重排要不要上**：RRF 之后如果仍不够，上 rerank（dashscope 有现成模型）；届时
   「召回多少条送进精排」与 `k` 一起调，不能只调一个。
7. ~~**切块策略本身的收益有多大**~~ → **已回答（2026-10-26）**：固定字数切 200 字最好（RRF 93%），
   H2 语义切 + 前置标题在各档都没跑赢（90%）。详见 §3.2 的表。
   ⚠️ **但落地时仍要做成可切换的** —— 这个结论绑定在 `bge-small`（512 token）上，
   换成云端 v4（2000 字符）或别的模型必须重跑。而且「H2 切但不加标题」的消融**还没做**，
   所以「为什么 H2 切更差」目前只有推测。
