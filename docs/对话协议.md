# 对话 SSE 协议

> LiMo 对话流式端点协议说明。端点：`GET /api/chat/stream`（SSE，`text/event-stream`）。

## 请求参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `question` | string | 用户消息正文 |
| `doc_ids` | string | 逗号分隔的文档 id（当前选中文档 + 本条 @ 引用，前端 chatStore 组合去重） |
| `doc_refs` | string | JSON 数组 `[{docId, title}]` —— 本条消息 @ 引用的文档（存 user 消息供展示） |
| `conversation_id` | string | 已有会话 id；空则后端创建新会话 |
| `model_id` | int | 模型 id（可选，缺省用 scene_models.chat） |
| `follow_up` | int | `1` = 开启「追问建议」（2026-10-11）。⚠️ **关闭时根本不传该参数**（不是传 `=0`）—— 零回归靠这一点。开启后若模型未自主写出可用块，后端在流末**补调一次** LLM 并推 `followup` 事件（见下） |

## 事件流（每行 `data: {json}\n\n`）

| type | 字段 | 前端处理 |
|------|------|---------|
| `meta` | `conversation_id`, `context_window`, `budget`, `price_in`, `price_out` | 建立会话关联 + 上下文预算/价格（C2/C4：进度条数据源，price 未配置为 null） |
| `compressed` | `count` | 历史压缩（C3）：更早 N 条已摘要，前端提示条 |
| `agent_status` | `message` | 状态条（「正在分析问题...」「正在整理回答...」） |
| `tool_start` | `tool`, `args`, `display` | 创建工具气泡（进行中） |
| `tool_result` | `tool`, `summary`, `refs` | 更新工具气泡（完成）+ assistant 引用 chips。`refs` 为引用的文档列表（agent.py `_extract_refs`），chat.py 累积后存 assistant 消息 `docRefs`，前端 `onRef` 去重追加。⚠️ **刻意不独立成 `ref` 事件** —— 引用天然是「某次工具调用的产物」，拆成两个事件只会让前端多守一个「refs 到齐了吗」的状态 |
| `thinking` | `text` | 思考段流式（deepseek 系列 `reasoning_content`），前端折叠展示 |
| `text` | `text` | 回答正文增量（打字机） |
| `done` | `cancelled?` | 流式结束；`cancelled=true` 表示被取消（部分内容已保存）。**不带 usage**（C4 token/费用统计依赖 `meta.price_in/price_out` + 前端 token 估算） |
| `followup` | `questions`, `error` | 追问建议（2026-10-11，**推在 `done` 之后**）：`questions` 为问题数组（可能为空）；生成失败时 `questions: []` + `error` 给文案 —— **开了开关却什么都没有必须看得出是失败**，不静默。⚠️ 前端 `parseSSEStream` 读到**流关闭**才 `break`（不因 `done` 类型停止），故晚推收得到；而 `done` 一到输入框即可用，用户不必等这几秒 |
| `error` | `message` | 出错 |

> **产物侧的 `followup` 事件**（2026-10-11，**不属于本协议**，列在这里只因它同名同形）：产物生成端点
> `GET /generate/{id}/stream` 也会推 `followup`，payload 多两个字段 —— `mode`（固定 `"notes"`）与
> `version`（追问挂在哪一版产物上）。差异的根源是**要落位的对象不同**：对话侧挂在**消息**上
> （`ChatMessage.follow_ups`），产物侧要挂在**版本**上（旁路文件 `notes/v{N}.followups.json`）。
> 其余语义一致（独立第二次调用 / 推在 `done` 之后 / 失败给 `error` 不静默 / 先写盘再推事件）。
> ⚠️ 前端 [api/generate.ts](../frontend/src/api/generate.ts) 里这一支**必须排在 `else if (data.mode)` 之前** ——
> 产物侧正文 chunk 恰恰带 `mode`，顺序写反会把追问事件当成正文塞进笔记（`text` 缺失 ⇒ 空 chunk），
> **零报错**。与 `stage` / `reasoning` 两支同款陷阱。

> **上下文预算（C2）**：`budget = context_window × 0.7`，历史按 token 反向裁剪（`trim_history`），文档引用按预算富余分级截断（2000/1000 字符）。
> **历史压缩（C3）**：未压缩历史 > 预算×60% 时 LLM 摘要早期消息 → `compressed` 事件 + 摘要并入 system prompt；压缩模型 fallback deepseek-flash → 当前模型 → 跳过本轮。

## 持久化

- 请求开始时后端 `append_user_message`（含 `doc_refs`）
- 流式结束后 `append_assistant_message`（含 `doc_refs` / `tool_calls` / `thinking` / **`follow_ups`**（2026-10-11，追问补调的结果）扩展字段）。⚠️ **先落库、再推 `followup` 事件** —— 反过来会让「写库失败」变成「前端有卡、刷新后没了」这种自相矛盾的状态。⚠️ `ChatMessage.to_dict()` 是**显式白名单**，新字段不加进去就是在**写盘那一刻**丢掉（症状：刷新后卡片消失）
- **中断**（客户端 abort → 后端 cancel_event → `done+cancelled`）：部分回复也会保存

## 正文语义标记（`limo-block`）

模型可以在回答正文里写语义标记，程序按标记渲染 —— 与产物侧的 `limo-block`
**同一套协议、不同的一套类型**（两侧集合不相交，各教各的）：

```
<!-- limo-block:v1 type="card-group" -->   ← 并列比较 2–4 个同级对象时 → 并排卡片
### 方案 A
...
<!-- /limo-block -->
```

| 类型 | 渲染 | 规范出处 |
|------|------|---------|
| `card-group` | 块内 `###` 各成一张并排卡片（可横着扫） | `app/agent/prompts/formats.md` |
| `follow-up` | 块内每个列表项一颗**可点击**的追问 chip（点了直接发送） | 同上 |
| `info` | 信息卡（讲清一个对象，值得被单独框出来、之后可能回来查） | 同上 |
| `digest` | 摘要卡（长回答**开头**的 2–5 条压缩要点） | 同上 |

⚠️ **总量闸门**：四种块**合计不超过两块**（逐条判据管「这一块该不该用」，闸门管「一次
回答用几块」—— 缺了后者，模型可以每一块都「判据成立」）。

- **注入**：`formats.md` 是 system prompt 的**静态**一层（`PromptLoader.build()`，
  `base + rules + formats + doc_context`），**无条件注入、无勾选项**。
- **存储**：原文一字不动地落盘（含标记行）—— 重开会话 / 编辑消息后**重新解析**即可复原，
  不需要任何额外字段。
- **渲染**：`ai-chat/ChatMarkerContent.tsx`。⚠️ **不复用产物侧的 `preview/MarkerContent`** ——
  它内部硬编码 `MarkdownPreview`（代码高亮 / 图片 zoom / 标题锚点），复用等于把整个对话正文
  换成产物渲染路径，波及**全部历史消息**。共享的只有**判据**（`parseMarkers` / `splitByHeading`）。
- **流式**：尾部的**半截标记行**被抑制（`markdown-scan.ts::suppressTrailingPartialMarker`），
  否则 chunk 把开标记切在中间时用户会看到原始协议文本飘过。
- **导出**：`.md` 剥标记行（`export.py` 的 `_strip_blocks`），`.json` **刻意保留**（可回灌）。
- **复制**：剥标记（`stripMarkers`）—— 复制的是用户看到的内容。
- **LLM 历史**：发给模型的上一轮原文**含**标记（让它看到自己写过的格式，强化一致性）。
- **降级**：未闭合 / 未知 type / 未知协议版本 → 只剥标记行、内容原样渲染（**零残留**）。

## 追问建议（用户可选开关）

`follow-up` 有**两个来源**，**渲染同一个组件、存储互不相干**：

1. **模型自主写的块** —— 正文里的 `<!-- limo-block:v1 type="follow-up" -->`（见上节）。
   走前端 `parseFollowUpItems` 解析 → `ChatFollowUpList`，条数**原样呈现**（不清理）。
2. **后端补调**（2026-10-11）—— 用户开启「追问建议」开关（请求参数 `follow_up=1`）后，
   若模型**没写出可用的块**，后端在 `done` 之后**独立调一次** LLM 生成追问，走
   `followup` 事件 → `ChatMsg.followUps` → 会话消息 `follow_ups` 落盘。这条路的输出
   经**去重 / 过滤过短 / 截 6 条**（清的是 LLM 原始输出）。
   ⚠️ **绝不写进 `content`**：追问是附属产物 ⇒ 导出路径只读 `content`、**天然不含候选
   问句**；而「被采纳的追问」是普通 user/assistant 消息、正常进产物（正是「像正常文章
   一样排布」要的）。

⚠️ 两条来源由后端保证**互斥**，判据 `has_usable_followup` = 「有块 **且** 块里抽得出问题」。
**只判「有块」是不够的**：模型写个空壳块（有标记、块内无列表）时前端抽不出项、整块退化
成普通正文，而后端以为「模型写过了」跳过补调 ⇒ **开了开关却一张卡都没有**（静默违反
承诺）。故后端判据必须 **≥ 前端严格度**。
⚠️ 追问生成**复用对话的 `llm` 实例、绝不 `aclose()`**（关了就顺手把对话连接池一起关掉）；
失败一律吞掉返回 `None`，**「显式」由 `followup` 事件的 `error` 字段承担**。
⚠️ **追问的追问天然成立**：补调发生在**每一轮**流结束，点 chip 走 `sendMessage`、新请求
照带 `follow_up=1` —— 刻意不设轮次上限（用户选的就是「一定会有」）。

## 相关 API

| 端点 | 说明 |
|------|------|
| `GET /api/conversations` | 会话列表（按 `updated_at` 降序） |
| `GET /api/conversations/{id}` | 完整会话（含 messages 扩展字段） |
| `POST /api/conversations` | 新建空会话 |
| `PATCH /api/conversations/{id}/append` | 追加一条消息（body `{role, content}`） |
| `PATCH /api/conversations/{id}` | body `{archived: bool}` —— 归档/取消归档 |
| `PATCH /api/conversations/{id}/rename` | 重命名 |
| `POST /api/conversations/{id}/clear-context` | body `{index}` —— 清除上下文边界（C4：该索引前消息不再携带、不参与压缩） |
| `PUT /api/conversations/{id}/messages` | 全量重建消息列表（编辑/删除/分支截断统一入口） |
| `DELETE /api/conversations/{id}` | 删除会话 |

## 前端映射

`api/chat.ts streamChat` → `store/chatStore.ts` 流式状态机：

| 事件 | chatStore action |
|------|------------------|
| `meta` | 建会话 + 插入列表；存 `contextWindow`/`budget`/`priceIn`/`priceOut` |
| `compressed` | `compressedHint` 提示条（更早 N 条已摘要） |
| `text` | `onText` → content 增量 |
| `tool_start` / `tool_result` | 工具气泡 running → done；`tool_result.refs` 同时喂 assistant `docRefs`（去重追加） |
| `thinking` | assistant `thinking` 累积 |
| `done` | `streaming=false` + 刷新列表。⚠️ **不含 usage**——C4 的 token / 费用统计由 `meta.price_in/price_out` + 前端 token 估算得出（见上表 `done` 行） |
| `error` | `isError` + `streaming=false` |
